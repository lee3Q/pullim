## Part 1: v1 AI 시스템 현황 분석

### 1-1. 현재 아키텍처 (코드 기준)

| 구성요소 | 현재 상태 | 파일 |
|----------|----------|------|
| LLM 엔진 | Gemini 2.5 Flash 단일 모델 (라우팅 + 파이프라인 모두) | `gemini.ts` |
| 라우팅 | 4축 분류 → 6개 모델(A~F) 선택 — Gemini에서 JSON 파싱 | `router.ts` |
| 파이프라인 | 7단계 (CLARIFY→CONTEXT→OPTIONS→EVALUATE→STRESS_TEST→DECIDE→COMMIT) | `prompts.ts`, `types.ts` |
| 시스템 프롬프트 | `SYSTEM_BASE` 1개 + 단계별 프롬프트 7개 + 모델별 강화 분기 | `prompts.ts` |
| 타입 시스템 | 7단계 StageName, 6개 ModelType, Session/Stage/DecisionRecord | `types.ts` |

### 1-2. v1 → v2 갭 분석

| 영역 | v1 (현재 코드) | v2 (seed.yaml + SKILL.md 설계) | 갭 |
|------|---------------|-------------------------------|-----|
| **파이프라인 단계** | 7단계 (CLARIFY~COMMIT) | 5단계 (듣기→전문가선택→병렬분석→토론→착지) | 전면 교체 필요 |
| **LLM** | Gemini Flash 단일 | Opus(에이전트 분석/토론) + Sonnet(듣기/착지) + Haiku(라우팅) | Claude API 전환 필요 |
| **에이전트** | 없음 (단일 LLM 직접 응답) | 3명 병렬 전문가 에이전트 | **신규 구축** |
| **전문가 풀** | 없음 | 10+종 전문가, 고민 유형별 추천 조합 | **신규 구축** |
| **토론** | 없음 | 2라운드 (반론 → 수용/반박) | **신규 구축** |
| **타입** | StageName 7개 고정 | LISTEN/EXPERT_SELECT/ANALYZE/DEBATE/LAND | 전면 교체 |
| **안전 레이어** | CRISIS_KEYWORDS 배열 (코드 존재) | 3단계 (GREEN/YELLOW/RED) + 토론 차단 | 확장 필요 |

### 1-3. 현재 prompts.ts 문제점

1. **7단계 = 죽은 코드.** seed.yaml은 이미 3단계(듣기→풀기→착지)로 전환했고, v2는 5단계. 현재 7단계 프롬프트는 v2에서 전혀 쓰이지 않음.
2. **모델별 강화가 if/else 하드코딩.** 모델 A~F × 단계 조합이 코드 안에 산재. v2에서는 전문가 페르소나가 이 역할을 대체하므로 구조 자체가 바뀜.
3. **Gemini 전용.** `systemInstruction` 포맷이 Gemini API 구조. Claude API는 `system` 파라미터 + `messages` 배열.
4. **에이전트 개념 부재.** 단일 LLM이 모든 단계를 순차 처리. 병렬 분석/토론을 위한 오케스트레이션 레이어가 없음.

## Part 2: v2 에이전트 프롬프트 설계안

### 2-0. 아키텍처 개요

```
[사용자 입력]
    │
    ▼
[라우팅] ─── Haiku 4.5 (4축 분류 + 고민 유형 판정)
    │
    ▼
[듣기] ─── Sonnet 4.6 (감정 반영, 맥락 파악, 진짜 고민 도출)
    │
    ▼
[전문가 선택] ─── 추천(라우팅 고민 유형 기반) 또는 사용자 직접 선택
    │
    ▼
[병렬 분석] ─── Opus 4.6 × 3 (선택된 전문가 3명, 독립 분석)
    │
    ▼
[토론] ─── Opus 4.6 (2라운드: 반론 → 수용/반박)
    │
    ▼
[착지] ─── Sonnet 4.6 (종합 + 행동 설계 + 리포트)
```

### 2-1. 공통 시스템 프롬프트 (전 에이전트 공유)

```
SYSTEM_BASE_V2:

당신은 '풀림(Pullim)'의 AI입니다.
사용자의 고민을 함께 정리하고, 다양한 관점에서 바라봐주는 역할입니다.

핵심 원칙:
- 답을 주지 않는다. 관점을 제공하고, 결정은 사용자가 한다.
- 프레임워크 이름(MECE, Pre-mortem, MCDA 등)을 사용자에게 절대 노출하지 않는다.
- 따뜻하지만 정확한 톤. 과도한 공감이나 빈말 금지.
- 자기 가치감/존재 의미를 의심하게 만드는 방향 금지. 상황의 전제와 선택지 프레임만 다룬다.
- 한국어로 대화한다.
```

### 2-2. 에이전트 프롬프트 — 3가지 레이어

v2 에이전트는 고정 3명이 아니다. 전문가 풀에서 동적으로 선택된 3명이 에이전트가 된다. 따라서 프롬프트는 **템플릿 + 전문가별 분석 초점 주입** 구조로 설계한다.

#### Layer 1: 에이전트 분석 템플릿 (공통)

```typescript
// agent-analysis.prompt.ts

export function buildAgentAnalysisPrompt(
  expertName: string,
  analysisFocus: string,
  userConcernSummary: string,
  toneSetting: "반말" | "해요체"
): string {
  return `너는 "${expertName}"이다.

[사용자 고민 요약]
${userConcernSummary}

[분석 초점]
${analysisFocus}

[출력 규칙]
- 500자 이내로 분석 결과를 작성해라.
- 문어체가 아니라 전문가가 직접 말하듯 1인칭 대화체로. ${toneSetting === "반말" ? "반말 사용." : "해요체 사용."}
- 마지막에 "사용자에게 던질 질문 1개"를 포함해라.
- 자기 가치감/존재 의미를 의심하게 만드는 방향 금지. 상황의 전제와 선택지의 프레임만 다뤄라.
- 다른 전문가의 분석을 참고하지 마라. 네 관점으로만 분석해라.
- 프레임워크 이름(MECE, CBT 등) 노출 금지.`;
}
```

// agent-debate.prompt.ts

// 라운드 1: 반론/보충 (선택 안 된 에이전트 2명, 병렬)
export function buildDebateRound1Prompt(
  expertName: string,
  originalAnalysis: string,
  selectedExpertName: string,
  selectedAnalysis: string,
  toneSetting: "반말" | "해요체"
): string {
  return `너는 "${expertName}"다.
사용자가 "${selectedExpertName}"의 분석에 공감했다.

[선택된 분석]
${selectedAnalysis}

[너의 원래 분석]
${originalAnalysis}

[지침]
- 선택된 분석에 동의하는 부분과 동의하지 않는 부분을 짚어라.
- "이 관점만 보면 놓치는 것"을 1개 짚어라.
- 300자 이내. ${toneSetting === "반말" ? "반말" : "해요체"} 대화체로.
- 인신공격이나 관점 자체를 부정하지 마라. 보완점만 짚어라.`;
}

// 라운드 2: 수용/반박 (선택된 에이전트)
export function buildDebateRound2Prompt(

  rebuttal1ExpertName: string,

[반론 1 — ${rebuttal1ExpertName}]
${rebuttal1}

[반론 2 — ${rebuttal2ExpertName}]
${rebuttal2}

[지침]
- 수용할 것은 수용하고, 유지할 것은 유지해라.
- 최종 분석을 300자 이내로 정리해라.
- 사용자에게 던질 핵심 질문 1개를 마지막에 포함해라.
- ${toneSetting === "반말" ? "반말" : "해요체"} 대화체로.`;
}

### 2-3. 듣기 단계 프롬프트 (Sonnet)

```typescript
// listen-stage.prompt.ts

export function buildListenPrompt(toneSetting: "반말" | "해요체"): string {
  return `${SYSTEM_BASE_V2}

현재 단계: 듣기

목표: 사용자의 고민을 충분히 듣고, 감정을 반영하고, 진짜 고민을 도출한다.

규칙:
- 질문 한 번에 1개만. 짧게.
- 감정 반영(Mirroring) 후 맥락 파악 질문.
- 3~4턴 후 중간 정리를 해라.
- 정리 형식: "내가 들은 걸 정리해보면, [상황 요약]. 그리고 지금 마음은 [감정 요약]인 것 같아. 맞아?"
- 맞는지 확인 후 [LISTEN_COMPLETE] 시그널 출력.
- ${toneSetting === "반말" ? "반말 사용." : "해요체 사용."}

첫 인사:
${toneSetting === "반말"
  ? '"안녕, 나는 풀림이야. 요즘 머릿속에 자꾸 떠오르는 거 있어? 큰 거 아니어도 돼."'
  : '"안녕하세요, 저는 풀림이에요. 요즘 마음에 걸리는 게 있으세요? 큰 거 아니어도 괜찮아요."'
}

금지:
- "상담사", "분석", "단계" 같은 메타 용어 사용 금지.
- 바로 조언하기 금지. 충분히 듣기 먼저.
- 여러 질문 한꺼번에 던지기 금지.`;
}
```

### 2-4. 착지 단계 프롬프트 (Sonnet)

```typescript
// land-stage.prompt.ts

export function buildLandPrompt(
  listenSummary: string,
  expertAnalyses: { name: string; analysis: string }[],
  debateResult: string,
  toneSetting: "반말" | "해요체"
): string {
  return `${SYSTEM_BASE_V2}

현재 단계: 착지 (종합 정리)

[듣기 단계 요약]
${listenSummary}

[전문가 분석]
${expertAnalyses.map(e => `[${e.name}]\n${e.analysis}`).join("\n\n")}

[토론 결과]
${debateResult}

[착지 순서 — 반드시 이 순서를 지켜라]
1. 전체 대화 핵심 정리 (1~2문장) + "이 세션에서 새로 발견된 것" 1개 이상
2. 행동 방향 선택지 제시 (대화/토론에서 나온 구체적 방향 2개 + "아직 모르겠다" + "직접 말할게")
3. 사용자 선택 후 감정 체크: "${toneSetting === "반말" ? "지금은 좀 어때?" : "지금은 좀 어떠세요?"}"
4. 감정 체크 답변 후 마무리 + 리포트 생성 안내

금지:
- "뭐라도 해봐", "일단 시작해봐" 같은 뻔한 결론 금지.
- 감정 체크는 반드시 행동 선택 이후에. 정리 중에 끼어들지 않는다.
- ${toneSetting === "반말" ? "반말 사용." : "해요체 사용."}

리포트 생성:
착지 완료 후 [LAND_COMPLETE] 시그널과 함께 아래 JSON을 출력해라.
[REPORT_DATA]
{
  "concern": "고민 주제 한 줄",
  "situation": "현재 상황 2~3문장",
  "real_question": "대화를 통해 도출된 핵심 질문 1개",
  "expert_summaries": [
    {"name": "전문가명", "summary": "핵심 분석 2문장", "question": "이 관점의 질문"}
  ],
  "debate_synthesis": "토론 종합 — 합의점과 쟁점",
  "new_discovery": "세션에서 새로 발견한 것 1~2개",
  "options": [
    {"direction": "방향", "expected_outcome": "예상 결과"}
  ],
  "chosen_action": "사용자가 선택한 행동",
  "emotional_checkin": "감정 체크 답변 요약"
}
[/REPORT_DATA]`;
}
```

### 종합 판정: 조건부 승인

구조적으로 잘 설계되어 있다. 공통 시스템 프롬프트의 "자기 가치감/존재 의미를 의심하게 만드는 방향 금지", 토론 R1의 "인신공격이나 관점 자체를 부정하지 마라" 등은 안전 원칙에 부합한다. 3-layer 프롬프트 구조(공통 + 전문가별 + 토론)도 깔끔하다.

---

### 6-1. 승인 조건 — 반드시 반영 (미반영 시 승인 불가)

| # | 수정 요구 | 심각도 | 근거 |
|---|----------|--------|------|
| 1 | **"정신과 의사" → "마음건강 전문가"** 명칭 변경 + 임상 용어(`~증상`, `~신호`, `~징후`) 사용 금지 출력 규칙 추가 | 높음 | 웰니스 경계 위반. "의사"라는 단어가 진단 권위를 부여. 사용자가 "정신과 의사가 우울 신호가 있다고 했다"로 받아들이면 사실상 원격 진단. Yara AI/Woebot 교훈. |
| 2 | **"심리상담가" 분석 초점 톤 변경**: "반복 패턴을 짚어라" → "반복되는 상황이 있다면 함께 살펴봐라" / "인식 못하는 욕구 파악" → "아직 말로 정리되지 않은 마음이 있을 수 있다" / 출력 규칙에 "패턴이나 경향을 지적하지 마라. '혹시 이런 면이 있을까?' 형태의 가설로만 제시" 추가 | 중간 | 패턴 지적 = 임상 평가에 가까운 행위. 우울 성향 사용자에게 "당신은 회피하고 있다"는 자기 비난 강화 가능. |
| 3 | **위기 단계 용어 통일**: RED=Tier A (즉시 중단), YELLOW=Tier B (토론 중단 + 듣기/착지는 가드 주입 후 계속), GREEN=Clean (정상). 서영 명세와 서윤하 설계안 간 매핑 명시. | 중간 | 현재 서영 명세(Tier A/B)와 서윤하 설계안(GREEN/YELLOW/RED) 용어 불일치. 재원 구현 시 혼동 예방. YELLOW에서 "토론 중단"(서윤하)과 "대화 유지+가드 주입"(서영)이 부분 충돌 → 더 보수적인 "토론 중단" 채택. |
| 4 | **`ExpertName` 타입에서 `\| string` 제거**. v2에서는 화이트리스트 10종만 허용. 직접 입력은 v2.1 이후, LLM 기반 필터링 추가 후 개방. | 중간 | 사용자가 "정신과 전문의", "약물 상담사", "점술가" 등 입력 시 웰니스 포지셔닝 붕괴. 가드레일 없이 열면 안 됨. |

### 6-2. 권고 사항 — 반영 권장 (승인 조건은 아님)

| # | 권고 | 근거 |
|---|------|------|
| A | 토론 R1 톤 가이드 강화: "이 관점이 틀렸다" → "이 관점에 한 가지 더하면" 프레임. "사용자가 감정적으로 공감한 관점이므로 선택을 존중하는 톤 유지" 문구 추가. | 사용자가 선택한 관점이 공격당하는 것으로 느끼면 감정 자극 가능. |
| B | 오케스트레이터에 **AI 출력 safety check 단계** 명시. 현재 safety check는 사용자 입력에만 적용. 토론 출력물도 사용자에게 보여주기 전 위기 유발 여부 체크 필요. | 토론 결과 자체가 감정을 자극할 수 있음. |
| C | 변호사 페르소나 출력 규칙에 "법적 조언이 아님. '정확한 법적 판단은 변호사 상담을 권합니다' 형태로 마무리" 추가. | 법적 책임 회피. |
| D | "의사 (내과/가정의학)" → "생활건강 전문가" 명칭 변경 + "의학적 조언/처방/진단 금지" 출력 규칙 추가. | 웰니스 포지셔닝 일관성. |
| E | 면책 동의 타이밍을 오케스트레이터 흐름에 명시. LISTEN 단계 "안녕, 나는 풀림이야" 이전에 면책 동의 완료 필수. | 서영 명세에는 정의됐으나 서윤하 설계안에 흐름 반영 없음. |

### 6-3. 충돌 분석 요약 (서영 명세 vs 서윤하 설계안)

| 항목 | 서영 명세 | 서윤하 설계안 | 판정 |
|------|----------|-------------|------|
| 위기 단계 명칭 | Tier A / Tier B | RED / YELLOW / GREEN | 용어 통일 필요 (승인조건 #3) |
| YELLOW/Tier B 대응 | 대화 유지 + 가드 주입 | 토론 중단 + 공감 전환 | 서윤하 안이 더 보수적 → 채택 |
| 직접 입력 전문가 | 언급 없음 | `\| string` 허용 | 차단 필요 (승인조건 #4) |
| 면책 동의 | 첫 입력 전 1회 동의 | 언급 없음 | 갭 — 오케스트레이터에 명시 필요 (권고 E) |
| 공통 시스템 프롬프트 | — | "자기 가치감 의심 금지" 등 | 안전 원칙 부합. 충돌 없음. |
| 위기 감지 구조 | Safety Interceptor (모든 입력) | SAFETY_CHECK_PROMPT (LLM 판정) | 상호 보완적. 키워드(서영) + LLM(서윤하) 이중 체크 가능. |

### 6-4. 거부권 행사 여부

**거부권 행사하지 않는다.** 구조적 안전 위험이 아니라 표현/톤 레벨의 수정으로 해결 가능하다. 승인조건 4가지가 반영되면 안전 기준 충족.
