### 1. "기술적으로 1인 개발이 가능한 이유" — 심사위원 납득용 논거

심사위원이 "개발자 없이 어떻게 만들어요?"라고 물으면, 사실 이 질문의 본질은 **"이거 진짜 만들 수 있어요?"**입니다. 답은 이미 나와 있습니다.

#### 논거 1: 이미 만들었다

22개 소스 파일, 1,642줄. 프론트엔드 + 백엔드 + AI 엔진 + 인프라 전체가 구현되어 있고, API key 연결하면 바로 동작합니다. "만들 수 있느냐"가 아니라 **"이미 만들었다"**가 답입니다.

| 모듈 | 구현 내용 | 상태 |
|------|----------|:----:|
| AI 구체화 엔진 | 3단계 파이프라인 + 4축 자동 라우팅 | 완료 |
| 대화 인터페이스 | 실시간 스트리밍 채팅 | 완료 |
| 정리 문서(첫 걸음) | 세션 → 구조화 문서 자동 변환 | 완료 |
| 위기 감지 | 키워드 기반 감지 + 전문기관 연결 | 완료 |
| 세션/상태 관리 | Zustand 기반 영속화 | 완료 |
| API 서버 | 스트리밍 + 라우팅 API | 완료 |
| 페이지/인프라 | Next.js + PWA + TypeScript | 완료 |

#### 논거 2: 2026년 기술 스택이 1인 풀스택을 가능하게 한다

5년 전이면 이 정도 시스템을 혼자 만드는 건 무모했습니다. 지금은 다릅니다.

| 과거 (2021) | 현재 (2026) | 효과 |
|-------------|------------|------|
| 프론트+백엔드 따로 개발 | **Next.js 15** — 프론트/백 통합, 하나의 프로젝트 | 개발 공수 50% 절감 |
| DB 설계 + 서버 운영 직접 | **Supabase** — DB/인증/스토리지/보안 올인원 | 서버 운영 공수 0 |
| 배포/CI/CD 직접 구축 | **Vercel** — git push만 하면 자동 배포 | 인프라 관리 공수 0 |
| AI 기능 직접 구현 (ML 팀 필요) | **Claude API** — API 호출 한 줄로 AI 대화 | ML 엔지니어 불필요 |
| 앱스토어 배포 (iOS/Android 각각) | **PWA** — 웹 하나로 모바일 앱 경험 | 네이티브 앱 개발자 불필요 |

비유하면, 예전에는 집을 지으려면 목수+전기+배관 다 따로 불러야 했는데, 지금은 **조립식 모듈 주택**입니다. 설계도(프롬프트 + 아키텍처)만 잘 짜면 1명이 조립할 수 있습니다.

#### 논거 3: AI 에이전트 = 개발 팀원

대표님이 쓰는 AI 에이전트 시스템은 단순한 코딩 보조가 아닙니다.

- **코드 작성**: 모듈 단위로 AI가 생성, 대표가 검토/통합
- **코드 리뷰**: 보안 취약점, 성능 이슈 자동 탐지
- **테스트 생성**: 단위 테스트 자동 작성
- **리팩토링**: 기술 부채 정리

기존 팀에서 주니어 개발자 2명이 하던 일을 AI 에이전트가 대체하고, 대표가 시니어 개발자처럼 설계/통합/검증 역할을 합니다. **코드 작성 속도는 3~5배**, 품질은 **지속적 자동 검증**으로 유지됩니다.

#### 논거 4: 우리 제품 특성상 1인 개발이 유리하다

풀림의 기술적 핵심은 **코드 복잡성이 아니라 프롬프트 품질**입니다.

| 구분 | 일반 앱 | 풀림 |
|------|---------|------|
| 핵심 난이도 | 코드 아키텍처 | 프롬프트 설계 + 코칭 로직 |
| 코드 역할 | 비즈니스 로직 전체 | AI를 서빙하는 인프라 |
| 코드 복잡도 | 높음 (수만 줄) | 중~낮음 (1,642줄로 전체 동작) |
| 전문인력 필요 | 프론트+백엔드+인프라 | **도메인 이해 + AI 프롬프트 + 기본 풀스택** |

코드가 하는 일은 "프롬프트를 API에 보내고, 결과를 예쁘게 보여주는 것"입니다. 핵심 가치는 코드 밖(프롬프트 + 파이프라인 설계)에 있고, 이건 대표님이 직접 설계하는 게 가장 빠릅니다. 오히려 개발자를 따로 두면 **"프롬프트 의도 → 코드 전달"** 커뮤니케이션 비용이 발생합니다.

### 2. 형(이상X)의 "기술 자문위원" 포지션이 기술 신뢰성을 보완하는 방법

1인 개발의 가장 큰 리스크는 **"기술적 판단 오류를 잡아줄 사람이 없다"**는 겁니다. 이걸 기술 자문위원이 해결합니다.

#### 자문위원 프로필

| 항목 | 내용 |
|------|------|
| 이력 | Google 해커톤 수상, 국내 해커톤 수상 |
| 오픈소스 | GitHub ~1,000 스타 프로젝트(Ouroboros) 제작/운영 |
| 역할 | 아키텍처 리뷰, 기술 의사결정 자문, 보안 점검 |
| 소통 방식 | 매일 카카오톡으로 진행상황 공유 + 코드 리뷰 |
| 관계 | 정식 팀원/공동창업자 아님. 기술 멘토 포지션 |

#### 이 구조가 동작하는 이유

- **일상적 리뷰**: 매일 카톡으로 "오늘 이 모듈 이렇게 짰는데 괜찮냐" → 즉시 피드백. 주 1회 코드 리뷰 미팅보다 빠르고 촘촘합니다.
- **아키텍처 검증**: 기술 스택 선택, DB 설계, 보안 구조 같은 큰 결정에서 경험 기반 검증. "Supabase RLS로 충분한가" 같은 판단을 혼자 하지 않습니다.
- **비용 0, 효과 80%**: 정규직 CTO가 하는 일의 80%를 자문 형태로 커버합니다. 코드를 직접 짜는 건 대표님이 하되, **"이 방향이 맞는가"**는 검증받는 구조입니다.
- **대표 성장 가속**: 매일 기술 피드백을 받으면서 대표님의 개발 역량이 빠르게 성장합니다. 이 과정 자체가 팀 기술력 누적입니다.

#### 심사위원용 표현

> "1인 개발이지만 혼자 판단하지 않습니다. Google 해커톤 수상, GitHub 1,000스타 프로젝트 운영자인 기술 자문위원이 매일 아키텍처와 코드를 검토합니다. 실행은 1인, 검증은 2인 체제입니다."

### 2. "1인 AI-Native 개발"을 약점이 아니라 차별점으로 전환하는 프레이밍

#### 프레이밍 전략: "약점 인정 → 구조적 장점 전환 → 증거 제시"

심사위원 머릿속에는 이런 공식이 있습니다:
> "좋은 아이디어 + 실행력 있는 팀 = 가능성"

1인이라는 건 "팀"에 마이너스입니다. 이걸 뒤집으려면 "실행력"에 압도적 플러스를 줘야 합니다.

#### 전환 프레임 3단계

**[1단계] 인정하되 재정의**

| 심사위원 인식 | 우리가 전달할 인식 |
|-------------|-----------------|
| "개발자 없이 어떻게?" | "개발자가 필요한 제품이 아닙니다" |
| "혼자서 다 하겠다고?" | "핵심 의사결정을 한 사람이 빠르게 내립니다" |
| "스케일 안 되지 않냐" | "MVP까지는 1인이 가장 빠르고, 이후에 확장합니다" |

**[2단계] 업계 사례로 정당화**

> - **Pieter Levels** (Nomad List, RemoteOK): 1인 개발로 월 $200K+ 매출. "팀을 키우면 느려진다"
> - **Notion 초기**: Notion 공동창업자 2명이 2년간 코드만 짰다. 팀 확장은 PMF 이후.
> - **국내 AI 스타트업 트렌드**: 2~3인 팀이 AI 도구 활용해 10인 팀 속도로 MVP 출시

풀림은 이 흐름의 극단적 형태입니다. **AI 에이전트가 주니어 개발자 2~3명 역할을 하고, 대표가 시니어로서 설계/통합/검증을 합니다.**

**[3단계] 증거로 마무리**

| 증거 | 의미 |
|------|------|
| 22파일 / 1,642줄 구현 완료 | "만들겠다"가 아니라 "만들었다" |
| 세션당 200원 비용 설계 | 기술+비즈니스 양쪽 이해 |
| 3단계 파이프라인 + 4축 라우팅 | 단순 챗봇이 아닌 체계적 엔진 |
| 기술 자문위원 일일 리뷰 | 1인이되 검증 구조 존재 |

#### PPT 슬라이드 16(팀 소개)에 반영할 문구

기존:
> "향후 팀 구성 계획: 동아리 활동 중 UX 디자이너 1명, 마케터 1명을 모집하여..."

수정:
> **개발 체제**: AI-Native 1인 풀스택 개발 + 기술 자문위원(Google 해커톤 수상) 일일 코드 리뷰
> **향후 팀 확장**: MVP 출시 후 사용자 데이터 기반으로 UX 디자이너, 마케터 순차 영입

### 3. 팀 확장 로드맵 — 언제/어떤 조건에서/누구를 영입하는지

심사위원이 정말 궁금한 건 "지금 혼자냐"가 아니라 **"계속 혼자일 생각이냐"**입니다. 성장 의지와 계획이 있다는 걸 보여주면 됩니다.

#### 타임라인

| 시기 | 조건(트리거) | 영입 대상 | 이유 | 형태 |
|------|------------|----------|------|------|
| **3~5월** (현재~MVP) | - | 영입 없음 | MVP까지는 1인이 가장 빠름. 의사결정 지연 0. | 대표 1인 + 기술 자문 |
| **5~6월** (베타) | 베타 사용자 20명 확보 | **UX 디자이너 1명** | 사용자 피드백 기반 UI/UX 개선. 코드가 아니라 경험을 다듬는 단계. | 동아리 내 모집 or 외주 |
| **6~7월** (MVP 출시) | 유료 전환 의향 5명+ | **마케터 1명** | 초기 사용자 획득. SEO + 커뮤니티 운영. | 동아리 내 모집 |
| **출시 후 3개월** (PMF 검증) | 유료 100명 돌파 | **풀스택 개발자 1명** | 대표 혼자 감당 못하는 기술 부채 해소 + 기능 개발 속도 2배. | 정규 채용 or 인턴 |
| **출시 후 6개월** (스케일) | 유료 300명+ / B2B 파일럿 | **백엔드 엔지니어 1명** | 인프라 안정화, 보안 강화, B2B 커스터마이징. | 정규 채용 |

#### 영입 안 하는 이유가 영입하는 이유보다 중요하다

| 시기 | 왜 아직 안 뽑는가 |
|------|-----------------|
| 3~5월 | 제품 방향이 안 잡힌 상태에서 팀원 = 의사소통 비용. 수동 테스트로 가설 검증이 우선. |
| 5~6월 | 개발자가 필요한 게 아니라 사용자 눈이 필요한 시점. 디자이너가 먼저. |
| 6~7월 | 코드보다 사용자 확보가 병목. 마케터가 먼저. |
| PMF 이후 | 드디어 코드가 병목. 이때 개발자. |

> **Perplexity 리서치와 정확히 일치합니다**: "초기~MVP~유료 전환까지는 1인 충분, 유료 100명+ 부터 기술 파트너 필요."

#### 심사위원용 한 줄

> "지금 혼자인 이유는 팀원이 없어서가 아니라, **지금 단계에서 1인이 가장 빠르기 때문**입니다. 베타 이후 UX 디자이너, MVP 이후 마케터, PMF 이후 개발자 순서로 확장합니다. 순서가 중요합니다."
