## 1. 팀원별 의견

### 박도현 (PM & Strategy Lead) — 운영/프로세스 관점

> 대표님 문제 인식에 100% 공감합니다. 지금 우리 파일이 왜 비효율적이냐면, **"파일은 있는데 카탈로그가 없다"**는 거예요. 도서관에 책은 꽂혀 있는데 검색 시스템이 없는 상태.
>
> 그런데 **지금 새 팀원을 뽑는 건 반대합니다.** Customer Discovery 단계에서 팀원 5명은 이미 많아요. 신청서 D-2인데 온보딩 비용이 발생하면 오히려 속도가 떨어집니다.
>
> 제 제안: **COS 역할에 "파일 카탈로그 관리" 추가.** COS가 이미 team_state.yaml과 대시보드.md를 관리하고 있으니까, 파일 인덱스도 같은 맥락이에요. COS가 세션 시작 시 브리핑할 때 파일 카탈로그를 참조하면, 대표님이 파일을 직접 안 읽어도 맥락을 잡을 수 있습니다.
>
> **다음 행동:**
> 1. `파일_카탈로그.md` 만들어서 현재 모든 파일의 목적/생성일/상태를 1줄 요약
> 2. COS 브리핑 프로토콜에 "관련 파일 요약" 항목 추가
> 3. 팀원이 새 파일 생성 시 카탈로그에 자동 등록하는 규칙 추가

---

### 한재원 (CTO) — 기술적 구현 관점

> 대표님 말씀 듣고 바로 떠오른 건, **이거 자동화해야 한다**는 겁니다. 사람이 수동으로 파일 목록 관리하면 결국 안 하게 돼요. 3일이면 outdated됩니다.
>
> 현실적인 방법: **파일 인덱스를 YAML이나 Markdown으로 만들되, 세션 시작 시 COS가 `ls -R`로 파일 목록을 스캔하고 카탈로그와 대조하는 스크립트**를 돌리면 됩니다. 새 파일이 생기면 "카탈로그 미등록 파일 N개 있음" 경고가 뜨는 구조.
>
> 구현 비용? **30분이면 됩니다.** 셸 스크립트 하나면 충분해요. 복잡한 DB나 시스템 필요 없습니다.
>
> 새 팀원은 필요 없어요. 이건 **시스템 문제지 인력 문제가 아닙니다.** 카탈로그 파일 하나 + 검증 스크립트 하나면 해결됩니다.
>
> **다음 행동:**
> 1. `파일_카탈로그.yaml` 생성 — 경로/목적/생성일/상태/담당자 필드
> 2. `catalog-check.sh` 스크립트 — 실제 파일과 카탈로그 대조, 미등록 파일 경고
> 3. COS 브리핑 시 스크립트 자동 실행

---

### 서윤하 (AI Lead) — AI/프롬프트/세션 맥락 관점

> 대표님 문제의 핵심은 **"세션 간 맥락 유실"**이에요. 파일을 다시 읽는 이유가, 이전 세션에서 뭘 했는지/뭘 결정했는지 기억이 안 되니까요.
>
> 파일 카탈로그는 도현 말대로 필요한데, 저는 한 가지 더 제안합니다: **세션 브리핑에 "파일 변경 로그"를 추가하자.** 지난 세션에서 어떤 파일이 생겼고, 어떤 파일이 수정됐고, 핵심 변경이 뭐였는지를 COS가 1-2줄로 요약하면, 대표님이 파일을 안 열어도 맥락을 잡을 수 있어요.
>
> 이건 제가 프롬프트 관점에서 본 건데, COS 브리핑 프롬프트에 **"최근 변경 파일 top 5"** 항목을 넣으면 토큰 효율적이면서도 맥락 유지가 됩니다. 파일 전체를 읽는 게 아니라 카탈로그의 1줄 요약만 읽으면 되니까요.
>
> 새 팀원은 저도 반대. 이건 **COS 브리핑 프로토콜 개선**으로 해결 가능합니다.
>
> **다음 행동:**
> 1. COS 브리핑 템플릿에 `[최근 변경]` 섹션 추가
> 2. 카탈로그에 `last_modified` 필드 추가해서 변경 추적 가능하게
> 3. 세션 종료 시 COS가 카탈로그 갱신하는 규칙 추가

### 최서영 (Domain Expert + Ethics/Safety) — 안전/데이터 관점

> 파일 관리 시스템 자체에는 동의합니다. 다만 한 가지 우려: **민감 정보 분류가 필요합니다.**
>
> 우리 파일에는 인터뷰 데이터(개인정보 포함 가능), 사업 전략, 재무 계획 등이 섞여 있어요. 카탈로그를 만들 때 **`sensitivity` 필드를 추가**해서 공개/내부/민감으로 분류하는 게 좋겠어요. 지금은 팀이 작아서 괜찮지만, 나중에 팀이 커지거나 외부 투자자에게 자료 공유할 때 "이건 보여줘도 되는 건가?" 판단이 필요합니다.
>
> 특히 인터뷰 데이터는 동의 여부도 기록해야 해요. 심리상담 관련 사업이라 **데이터 취급에 더 민감해야** 합니다. 규제 관점에서 "우리는 초기부터 데이터 관리를 체계적으로 했다"는 게 나중에 신뢰도가 됩니다.
>
> 새 팀원 신설은 저도 시기상조라고 봅니다. 다만 **MVP 이후 사용자 데이터가 쌓이기 시작하면 DPO(Data Protection Officer) 역할은 검토**해야 합니다.
>
> **다음 행동:**
> 1. 카탈로그에 `sensitivity` 필드 추가 (public / internal / sensitive)
> 2. 인터뷰 데이터 파일에 동의 여부 메타데이터 포함
> 3. MVP 마일스톤에 "DPO 역할 검토" 항목 추가

## 2. 합의 사항

### 결론: 새 팀원 신설 불필요. COS 역할 확장 + 파일 카탈로그 시스템 도입.

**전원 합의 (4:0):**
- 현 단계에서 새 인력 추가는 **온보딩 비용 > 효과**
- 문제의 본질은 "인력 부족"이 아니라 **"시스템 부재"**
- COS가 이미 team_state.yaml / 대시보드.md를 관리하므로, 파일 카탈로그도 같은 레이어에서 관리

### 역할 정의: COS 파일 관리 기능 추가

| 항목 | 내용 |
|------|------|
| 담당 | COS (비서실장) |
| 산출물 | `~/study/main/창업/팀/파일_카탈로그.yaml` |
| 갱신 시점 | 세션 종료 시 (새 파일 생성/수정 발생 시) |
| 브리핑 반영 | 세션 시작 브리핑에 `[최근 변경]` 섹션 추가 |
| 검증 | `catalog-check.sh`로 미등록 파일 자동 탐지 (재원 설계) |

### 파일 카탈로그 형태 (합의안)

```yaml
# ~/study/main/창업/팀/파일_카탈로그.yaml
# 창업팀 파일 인덱스 — COS 관리
# 갱신: 세션 종료 시

files:
  - path: "제품/PRD_AI_의사결정_도우미_v1.md"
    purpose: "MVP 제품 요구사항 정의서"
    created: 2026-03-07
    last_modified: 2026-03-08
    owner: 박도현
    sensitivity: internal  # public / internal / sensitive
    status: active  # active / outdated / archived
    summary: "3단계 파이프라인, 4축 라우팅, 정리문서 생성 등 MVP 전체 스펙"

  - path: "제품/seed.yaml"
    purpose: "제품 핵심 스펙 (기술용)"
    created: 2026-03-07
    last_modified: 2026-03-08
    owner: 한재원
    sensitivity: internal
    status: active
    summary: "7단계 파이프라인, 6개 모델, 4축 라우팅 상세 스펙"

  # ... (모든 파일 등록)
```

### COS 브리핑 프로토콜 변경

기존 브리핑에 아래 섹션 추가:

```
[최근 변경 (지난 세션 이후)]
- 신규: {파일명} — {목적 1줄}
- 수정: {파일명} — {변경 내용 1줄}
- 미등록 파일: {N}개 (catalog-check 결과)
```
