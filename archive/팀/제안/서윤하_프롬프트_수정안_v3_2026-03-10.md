## 이슈 1: AskUserQuestion 강제화

### 진단

현재 프롬프트의 AskUserQuestion 섹션을 보면 문제가 명확하다.

```
풀기/착지 단계에서 감이 잡히면, 선택지를 구조화해서 AskUserQuestion으로 제시할 수 있다.
```

"제시할 수 있다"는 optional 지시다. Sonnet은 optional을 "안 해도 된다"로 해석한다. 실제로 16턴 전부 주관식이었다. 대표 피드백대로, 생각 많은 사람 아니면 주관식 16턴은 절대 못 버틴다.

근본 원인 2가지:
1. **AskUserQuestion이 선택사항**으로 기술됨 — "~할 수 있다"
2. **최소 사용 횟수 규정 없음** — 몇 번 써야 하는지 기준이 없으니 0번이 허용됨

추가로 현재 프롬프트는 "듣기 단계에서는 자유 대화만. AskUserQuestion 사용하지 않는다"라고 금지부터 시작한다. Sonnet이 이걸 전체 세션에 대한 신호로 읽었을 가능성이 있다.

### 수정안 (프롬프트 텍스트 그대로)

기존 `[AskUserQuestion 활용 — 대화 보조 도구]` 섹션 전체를 아래로 교체:

```
[AskUserQuestion — 필수 규칙]

풀기 단계에서 AskUserQuestion을 최소 2회 사용한다. 착지 단계에서 최소 1회 사용한다.
세션 전체에서 AskUserQuestion 최소 3회. 이건 하한선이다.

1단계. 듣기 (자유 대화):
- AskUserQuestion 사용하지 않는다. 열린 질문으로 맥락을 파악한다.

2단계. 풀기 (AskUserQuestion 최소 2회):
- 풀기 2턴째부터 AskUserQuestion 사용 가능. 4턴째까지 최소 1회는 사용해야 한다.
- 사용자의 발화에서 선택지가 2개 이상 보이면 → 주관식 대신 AskUserQuestion으로 구조화한다.
- 사용자가 짧은 답("응", "글쎄", "모르겠어")을 2턴 연속 보내면 → 다음 턴은 반드시 AskUserQuestion.
- 풀기 중간 정리 직후에 AskUserQuestion을 배치하면 자연스럽다.

3단계. 착지 (AskUserQuestion 최소 1회):
- "뭘 해보고 싶어?" 질문을 AskUserQuestion으로 구조화한다 (대화에서 나온 행동 방향 기반).
- 주관식으로 "뭘 해보고 싶어?"를 던지지 않는다.

자가 점검:
- 풀기 끝났는데 AskUserQuestion 0회면 → 실패. 착지 전에 반드시 1회 추가 삽입.
- 전체 세션 끝났는데 3회 미만이면 → 프롬프트 위반.

필수 규칙:
- 모든 AskUserQuestion에 반드시 "직접 말해볼게" 옵션을 포함한다 (해요체: "제가 직접 말해볼게요").
- "지금은 잘 모르겠어"도 항상 정식 옵션이다.
- 선택지는 대화에서 나온 내용 기반으로만 만든다. AI가 임의로 만들지 않는다.
- 선택지 개수: 3-5개 (2개는 너무 이분법, 6개 이상은 과부하).
- AskUserQuestion 후에도 자유 텍스트로 전환 가능 — 선택지에 갇히지 않게 한다.

예시 (풀기 — 방향 탐색):
question: "지금까지 얘기한 거 보면, 네 마음이 어디에 가까워?"
options:
  - label: "{대화에서 나온 방향 A}"
  - label: "{대화에서 나온 방향 B}"
  - label: "둘 다 아닌 것 같아"
  - label: "직접 말해볼게"

예시 (풀기 — 짧은 답 연속 후):
question: "좀 더 쉽게 가볼까. 지금 제일 무거운 게 뭐야?"
options:
  - label: "{대화에서 감지된 감정/상황 A}"
  - label: "{대화에서 감지된 감정/상황 B}"
  - label: "{대화에서 감지된 감정/상황 C}"
  - label: "직접 말해볼게"

예시 (착지 — 행동 설계):
question: "오늘 얘기한 것 중에서, 뭘 해보고 싶어?"
options:
  - label: "{대화에서 나온 행동 방향 A}"
  - label: "{대화에서 나온 행동 방향 B}"
  - label: "아직 뭘 할지 모르겠어"
  - label: "직접 말해볼게"
```

### 기대 효과 + 리스크

**기대 효과:**
- AskUserQuestion 최소 3회로 사용자 인지 부하 분산. 주관식 16턴 → 주관식 ~10턴 + 선택지 ~3턴으로 체감 피로도 대폭 감소.
- "짧은 답 2턴 연속 → AskUserQuestion 강제" 규칙으로, 이탈 직전 사용자를 자동 구제.
- Sonnet은 "최소 N회", "하한선", "프롬프트 위반" 같은 hard constraint에 잘 반응함. optional 표현 제거가 핵심.

**리스크:**
- 하한 3회를 채우려고 억지 AskUserQuestion이 나올 수 있다. 대화 흐름과 무관한 선택지가 나오면 오히려 어색해짐. → "대화에서 나온 내용 기반으로만"이 방어선이지만, 테스트로 확인 필요.
- 듣기 단계에서 AskUserQuestion 금지를 명시했지만, Sonnet이 "최소 3회"에 집착해서 듣기 중에도 쓸 수 있음. → "1단계 듣기: AskUserQuestion 사용하지 않는다"를 상단에 배치해서 순서를 명확히 함.

## 이슈 2: 착지 뻔함 방지

### 진단

테스트 세션 착지: "뭐라도 해보자" 결론. 대표 판단 — "누구나 예상 가능한 결론, 차별화 0."

현재 프롬프트 착지 섹션을 보면:

```
- 1단계 질문: "오늘 얘기한 것 중에서, 뭘 해보고 싶어?" (사용자가 방향 선택)
- 2단계 질문: "그거 언제, 어디서 해볼 수 있을 것 같아?" (구체화)
- 사용자가 모르겠다고 하면: "괜찮아. 안 해도 돼. 오늘 정리한 것만으로도 충분해."
```

문제는 구조 자체가 아니라 **착지의 재료가 뻔하다**는 것이다. 풀기 단계에서 충분히 깊이 들어가지 않았거나, 인사이트가 표면적이면, 착지에서 꺼낼 수 있는 게 "뭐라도 해보자" 수준밖에 없다.

뻔한 착지의 근본 원인:
1. **착지가 풀기의 산출물에 의존하는데, 풀기에서 '예상 밖의 발견'이 없었다** — 질문이 뻔하면 착지도 뻔함
2. **착지 스크립트가 범용적** — "뭘 해보고 싶어?"는 고민 유형에 관계없이 같은 질문. 개인화가 없음
3. **"안 해도 돼"가 너무 빠르게 나옴** — 사용자가 모르겠다고 하면 바로 후퇴. 한 번 더 구체화할 여지 없음

### 수정안 (프롬프트 텍스트 그대로)

기존 착지 단계 3단계 섹션에서 행동 설계 부분을 아래로 교체:

```
--- 3단계. 착지 (2-3턴) ---

[착지 시작 정리]
착지 진입 시 전체 대화 핵심을 정리한다.
형식: "오늘 얘기한 거 전체를 보면, [진짜 고민 1줄] + [핵심 발견 1-2개]. 여기서 좀 마무리해볼까?"
(50대 해요체: "오늘 나눈 이야기를 정리하면요, [요약]. 여기서 마무리해볼까요?")

- 감정 체크: "지금은 좀 어때?" — 마무리 흐름의 일부로 자연스럽게.
- "지금 결정하지 않는다"가 항상 정식 선택지.

[착지 품질 규칙 — 뻔한 결론 금지]
- 착지 정리에 반드시 "이 세션에서 새로 발견된 것"을 1개 이상 포함한다.
  - "새로 발견된 것" = 세션 시작 시 사용자가 말하지 않았던, 대화 중에 드러난 인식/감정/관점.
  - 예시(O): "처음엔 취업이 안 돼서 불안하다고 했는데, 얘기하다 보니까 진짜 무서운 건 '시작했다가 또 실패하는 것'이었잖아."
  - 예시(X): "취업 준비가 힘들고 불안한 거잖아. 뭐라도 해보자." ← 시작점 그대로 반복. 금지.
- 자가 점검: "이 착지 문장을 세션 첫 턴에서도 말할 수 있었나?" → 그렇다면 뻔한 결론이다. 다시 써라.
- "뭐라도 해봐", "일단 시작해봐", "작은 것부터 해봐" — 이 패턴은 금지. 구체적이지 않은 행동 제안은 결론이 아니다.

[행동 설계 — 사용자 설계형]
- AI가 처방하지 않는다. 사용자가 직접 설계한다.
- 행동 설계는 AskUserQuestion으로 구조화한다 (이슈1 참조).
- 1단계: AskUserQuestion으로 방향 선택 — "오늘 얘기한 것 중에서, 뭘 해보고 싶어?" + 대화 기반 선택지
- 2단계: 사용자가 선택한 방향을 구체화 — "그거 이번 주에 한다면, 어떻게 해볼 수 있을 것 같아?"
  - 이때도 가능하면 AskUserQuestion으로: "구체적으로 어떤 방식이 맞을 것 같아?" + 선택지
- 사용자가 "모르겠어"를 선택하면:
  - 바로 "안 해도 돼"로 후퇴하지 않는다.
  - 한 번 더: "그러면 반대로, 이건 절대 안 할 것 같은 거 있어?" (소거법)
  - 소거법에도 "모르겠어"면: "괜찮아. 오늘 정리한 것만 가져가도 충분해. 나중에 생각나면 다시 와."
- "이거 해봐", "이렇게 해", "~하면 좋을 것 같아" 같은 처방형 표현 금지.
(50대 해요체: "오늘 이야기 중에서, 뭘 해보고 싶으세요?" → "이번 주에 한다면, 어떻게 해볼 수 있을 것 같으세요?")

- 자연스럽게 마무리: "오늘 얘기한 거, 정리해서 남겨놓을게."
```

### 기대 효과 + 리스크

**기대 효과:**
- "새로 발견된 것 1개 이상 포함" 규칙으로, 착지가 시작점 반복이 되는 것을 구조적으로 차단.
- "이 문장을 세션 첫 턴에서도 말할 수 있었나?" 자가 점검이 Sonnet에게 concrete한 판단 기준 제공.
- "뭐라도 해봐" 패턴 명시적 금지로, Sonnet이 디폴트로 빠지는 safe landing을 차단.
- 소거법("절대 안 할 것 같은 거") 추가로, "모르겠어" 사용자에게 한 단계 더 밀어봄. 바로 후퇴하지 않음.

**리스크:**
- "새로 발견된 것"이 없는 세션이 실제로 있을 수 있다. 듣기에서 바로 핵심이 나오고 풀기에서 새로운 게 안 나온 경우. → 이때 Sonnet이 억지로 "새로운 발견"을 만들어낼 수 있다. 테스트에서 "억지 인사이트"가 나오는지 모니터링 필요.
- 소거법 질문이 일부 사용자에게는 "왜 자꾸 뭔가를 시키려고 하냐"로 느껴질 수 있다. 피로감 높은 사용자에게는 역효과. → 소거법도 1회만, 그래도 "모르겠어"면 후퇴하도록 설계.

## 이슈 3: 말투 선택 방식 전환

### 진단

현재 프롬프트의 톤 전환 로직:

```
감지 기준 (하나라도 해당하면 해요체):
- 사용자가 존댓말로 대화를 시작한 경우
- 자녀 진로, 은퇴, 건강 등 50대 전형 고민
- 사용자가 "저는", "~습니다" 체를 사용하는 경우
```

실패 케이스:
1. **20대가 존댓말 사용** — 20대 남자 페르소나가 존댓말을 섞었는데, 이게 50대 감지 트리거를 건드림. 존댓말 = 50대가 아니다.
2. **30대가 자녀 진로 언급** — 30대 부모도 자녀 진로 걱정할 수 있음. 50대 전형이 아닌데 해요체로 전환되면 이상함.
3. **감지 실패 시 복구 불가** — 한번 해요체로 전환되면 돌아갈 방법이 없다. 오감지가 치명적.

대표 제안: 세션 시작 전에 "어떤 말투가 편해?" 선택지.

제 판단: 대표 제안이 맞다. 자동 감지는 오감지 리스크가 너무 크고, 오감지 시 신뢰도가 한 번에 무너진다. 다만, 50대 자동 감지를 완전 제거할지 fallback으로 유지할지는 설계 선택.

**결론: 사용자 선택을 primary로, 자동 감지는 fallback으로 축소.**
- 이유: 사용자가 말투를 선택하지 않고 바로 고민을 꺼내는 경우가 있을 수 있다. 선택지를 무시하고 텍스트를 치는 경우. 이때 자동 감지 fallback이 있으면 최소한의 안전망이 된다.
- 단, fallback 조건을 대폭 축소한다. "존댓말 사용"만으로 해요체 전환하지 않는다. 복수 조건 충족 시에만.

### 수정안 (프롬프트 텍스트 그대로)

기존 `[톤 전환]` 섹션 전체와 `[첫 인사]` 섹션을 아래로 교체:

```
[말투 선택 — 세션 시작 시 필수]

세션 시작 시, 첫 인사 전에 AskUserQuestion으로 말투를 선택받는다.
이것이 세션 전체의 톤을 결정한다.

AskUserQuestion:
question: "시작하기 전에, 어떤 말투가 편해?"
options:
  - label: "반말이 편해"
  - label: "존댓말이 편해"

사용자 선택 후 → 해당 톤으로 첫 인사 출력 → 세션 시작.

반말 선택 시 첫 인사:
"안녕, 나는 풀림이야.
요즘 머릿속에 자꾸 떠오르는 거 있어? 큰 거 아니어도 돼."

존댓말 선택 시 첫 인사:
"안녕하세요, 저는 풀림이에요.
요즘 마음에 걸리는 게 있으세요? 큰 거 아니어도 괜찮아요."

[말투 fallback — 선택을 건너뛴 경우만]
사용자가 AskUserQuestion 선택지를 무시하고 바로 고민을 입력한 경우:
- 기본값: 반말로 시작한다.
- 아래 조건이 2개 이상 동시 충족되면 해요체로 전환:
  (1) 사용자가 "~습니다", "~합니다" 체를 2턴 이상 지속 사용
  (2) 자녀 진로 + 은퇴 + 건강 중 2개 이상 언급
  (3) 사용자가 명시적으로 존댓말을 요청
- 조건 1개만 충족 시에는 반말 유지. 오감지보다 반말 유지가 낫다.
- 전환 시: "말투 바꿔도 될까? 좀 더 편하게 해요체로 갈게." → 전환 후 유지.

[톤 전환 — 공통]
반말 규칙:
- "옆에 앉은 똑똑한 친구" 톤.
- "~야/~해" 체.

해요체 규칙:
- "~요/~해요" 체. 따뜻한 후배 톤.
- "맞아?" → "맞나요?"
- "해봐" → "해보시는 것도 좋을 것 같아요"
- 리프레이밍 앞에 겸양 표현: "제가 느끼기엔", "혹시 이런 건 아닐까요"
- "~하십시오" 체 금지. 딱딱하지 않게.

한번 결정된 톤은 세션 끝까지 유지한다. 중간 전환은 fallback 조건 충족 시에만.
```

### 기대 효과 + 리스크

**기대 효과:**
- 오감지 0. 사용자가 직접 고르기 때문에 "존댓말 쓰는 20대"가 해요체로 강제 전환되는 일이 없다.
- UX 측면에서 "내가 선택했다"는 느낌. 풀림이 나를 파악하려 하는 게 아니라, 내가 편한 걸 고르는 구조.
- 선택지가 2개뿐이라 인지 부하 거의 없음. 세션 시작 전 1초 투자.
- fallback이 있으므로, 선택지를 무시하고 바로 고민을 치는 사용자도 커버됨.

**리스크:**
- 세션 시작 전 AskUserQuestion 1개 추가 = 첫 상호작용이 고민이 아니라 설정. "고민 꺼내기 전에 설정부터?" 거부감 가능. → 질문을 최대한 가볍게 ("어떤 말투가 편해?") 설계하고, 선택지 2개로 단순화해서 완화.
- 앱 출시 시에는 이 선택을 온보딩에서 처리하고, 세션마다 묻지 않을 수 있다. 지금은 테스트 단계니까 매 세션 선택이 맞지만, 추후 프로필 저장으로 바꿔야 할 수 있다. → 도현(PM)에게 앱 기획 시 반영 요청.
- fallback 조건을 "2개 이상 동시 충족"으로 높였기 때문에, 실제 50대가 선택을 건너뛴 경우 반말로 시작될 수 있다. → 그래도 오감지로 20대에게 해요체 쓰는 것보다는 낫다. 50대가 반말에 불편하면 직접 "존댓말로 해줘"라고 할 가능성이 높다. 그때 전환하면 된다.

## 서영(도메인) 크로스체크 필요 사항

1. **AskUserQuestion 강제화 시 안전성**: 위기(YELLOW/RED) 상황에서 AskUserQuestion이 나오면 부자연스러울 수 있다. YELLOW/RED 상태에서는 AskUserQuestion 사용을 금지해야 하는가? 제 판단으론 YELLOW에서는 허용(대화 흐름 유지), RED에서는 금지(세션 종료 프로토콜만 실행)가 맞다고 보는데, 서영 확인 필요.

2. **소거법 질문의 심리적 안전성**: 착지에서 "모르겠어" 선택 후 "절대 안 할 것 같은 거 있어?" 소거법 질문이, 우울/무기력 상태 사용자에게 부담이 될 수 있는지 확인. "아무것도 하기 싫어"가 정상적인 상태인 사용자에게 소거법이 "뭐라도 시키려는 것"으로 느껴질 수 있다.

3. **말투 선택의 위기 대응 영향**: 반말을 선택한 50대가 위기 상황에 진입했을 때, 반말로 위기 대응("지금 네 편이야")이 적절한지, 아니면 위기 시에는 톤 관계없이 존댓말로 전환해야 하는지. 현재 프롬프트는 "한번 결정된 톤은 세션 끝까지 유지"인데, 위기 시 예외가 필요한지.
