## 1. 기술 아키텍처 비판

### 1.1 v2 파이프라인 복잡성 — 과잉 설계 [심각도: 높음]

**문제**: 분류(Haiku) -> Socratic 듣기(Sonnet) -> 전문가 선택 -> 에이전트 병렬 분석(Opus x3) -> 토론(2라운드) -> 착지 + 리포트.

하나의 사용자 세션에 최소 **7~9회의 LLM API 호출**이 발생한다. 분류 1회 + 듣기 N턴 + 분석 3회(병렬) + 토론 R1 3회 + 토론 R2 3회 + 착지 1회. 이것은 "파이프라인"이 아니라 **파이프라인 스파게티**다.

**근거**:
- 각 호출 사이에 상태를 관리해야 하는데 DB가 없다. 모든 상태가 메모리/클라이언트에 의존한다.
- 호출 하나가 실패하면 전체 세션이 무너진다. 재시도 로직, 부분 실패 처리, 타임아웃 핸들링이 코드에 보이지 않는다.
- Opus x3 병렬 호출은 동시에 3개의 고비용 API 요청을 보낸다. Anthropic rate limit(RPM)에 걸릴 확률이 높다. 특히 무료 티어나 초기 API 계정은 RPM이 낮다.

**비교**: 내가 만든 AI SaaS 3개 중 가장 복잡한 것도 세션당 LLM 호출이 3회였다. 7~9회는 MVP에서 할 짓이 아니다.

### 1.2 Opus x3 병렬 호출의 비용/지연 [심각도: 치명적]

**문제**: v2 세션당 원가 543원이라고 했다. CTO(에이전트)의 이전 분석에서는 Sonnet 기준 198원이었는데, v2에서 Opus 하이브리드로 전환하면서 **2.7배** 뛰었다.

**계산**:
- Opus input $5/1M + output $25/1M. 분석 3명 + 토론 R1 3명 + R2 3명 = 최대 9회 Opus 호출
- 유저 100명, 월 4회 세션 가정 시: 543원 x 400 = **월 21.7만원 API 비용**
- 월 수익: 유료 전환율 4% 가정 -> 4명 x 7,500원 = **3만원**
- **API 비용만으로 월 수익의 7.2배를 태운다.**

**지연**: Opus 한 번 호출에 평균 5~15초. 3개 병렬이면 가장 느린 놈 기준 15초. 이걸 2라운드 하면 토론만 30초. 전체 파이프라인이 **60~90초**. 사용자가 기다리겠나?

### 1.3 DB 부재 — 제품이 아니라 데모 [심각도: 치명적]

**문제**: Supabase "계획만" 있고 구현은 없다.

**결과**:
- 세션 데이터가 축적되지 않는다. 그런데 차별화 모트가 "축적 데이터 록인"이라고 한다. **데이터를 저장하지 않으면서 데이터 록인을 주장하는 것은 모순이다.**
- 사용자가 브라우저를 닫으면 모든 것이 사라진다.
- 정리 문서(첫 걸음)의 공유 링크? 영속 스토리지 없이 어떻게 공유하나?
- 분석/토론 결과를 학습에 활용할 방법이 없다.

### 1.4 단일 장애점(SPOF) [심각도: 높음]

**문제**:
- Anthropic API가 다운되면 서비스 전체가 죽는다. 폴백 없음.
- Vercel 서버리스 함수의 실행 시간 제한(기본 10초, Pro는 60초). v2 파이프라인이 60초 이상 걸리면 타임아웃.
- `claude.ts`에서 싱글턴 패턴으로 클라이언트를 만들지만, 서버리스 환경에서 싱글턴은 콜드 스타트마다 재생성된다. 성능 이점이 사실상 없다.

### 1.5 확장성 [심각도: 중간]

**문제**: 현재 구조로 동시 사용자 10명만 되어도 문제가 생긴다.
- Opus x3 병렬 = 동시 사용자 10명이면 30개의 Opus 요청이 동시에 간다. Anthropic rate limit 확실히 걸린다.
- SSE 스트리밍이 Vercel 서버리스에서 어떻게 동작하는지 검증한 적이 없어 보인다.
- 에러 핸들링: 36차에서 "Critical 1건(ReadableStream try/catch) 즉시 수정"이라고 했는데, 이건 검증 없이 코딩했다는 뜻이다.

## 2. AI 에이전트 팀 비판

### 2.1 에이전트 팀의 실제 효과 [심각도: 높음]

**문제**: 4명의 AI 에이전트(CTO, AI Lead, PM, Domain Expert)가 "팀"을 구성하고 있다. 이것의 실체는 **같은 LLM에 다른 시스템 프롬프트를 넣고 순차 호출하는 것**이다.

**비판**:
- CTO 에이전트가 코드 리뷰를 하지만, 실제로 코드를 실행하거나 테스트하지 않는다. 36차에서 COS가 직접 코드를 작성했다. 그러면 CTO 에이전트가 왜 필요한가?
- AI Lead 에이전트가 프롬프트를 설계하지만, "한 명도 실제로 안 써봄"이라고 스스로 회고했다. 457줄짜리 프롬프트 설계안이 실사용자 없이 나온 것이다.
- 팀원의 자체 회고가 이미 문제를 정확히 짚고 있다: "코드 없는 CTO", "설계 전부 이론 기반", "안전이 후반에 끼워맞춰짐". **자기 진단은 했는데 행동이 안 바뀌었다는 게 더 큰 문제다.**

### 2.2 "팀 회의"의 토큰 낭비 [심각도: 높음]

**문제**: 회의록 9건, 37차 세션. 라운드 1(병렬) + 라운드 2(크로스체크) 구조.

**계산**:
- 에이전트 1명 소환 = 프롬프트 파일 읽기 + 안건 + 맥락 + 관련 파일 = 최소 3,000~5,000 토큰 input
- 4명 병렬 = 12,000~20,000 토큰 input + 각 발언 output 4,000~8,000 토큰
- 라운드 2까지 하면 토큰 2배
- **한 번의 "팀 회의"에 대략 50,000~80,000 토큰**. Claude Max 구독(145만원) 내에서 소화한다고 해도, 이 토큰이 **제품 개발이 아니라 회의에 쓰이고 있다.**

**핵심 질문**: 37차 세션 동안 에이전트 팀이 만든 산출물 중, 실제 코드로 반영된 것이 몇 개인가? 대시보드를 보면 코드 작성은 36~37차에서 COS가 직접 했다. 나머지 35개 세션은 뭘 한 건가?

### 2.3 에이전트 간 크로스체크의 한계 [심각도: 중간]

**문제**: "라운드 2 크로스체크 필수"라는 규칙이 있다. 하지만 같은 LLM이 다른 페르소나를 쓰고 서로 "검토"하는 것은 **동의 편향(agreement bias)의 구조적 재생산**이다.

**근거**:
- 크로스체크에서 "승인3 + 수정4"라고 되어 있는데, 수정 내용을 보면 "명칭 변경", "톤 변경" 같은 표면적 피드백이다. "이 기능 자체가 필요 없다" 수준의 근본 비판은 나오지 않았다.
- 에이전트끼리 "전원 합의"를 자주 도출하는데, 이건 합의가 쉽기 때문이 아니라 **같은 모델이 같은 방향으로 편향되기 때문**이다.

### 2.4 COS 운영 오버헤드 [심각도: 중간]

**문제**: COS(비서실장) = Claude가 팀 운영을 한다. 세션 시작마다 세션_맥락.md + team_state.yaml + 대시보드.md를 읽고, 브리핑을 만들고, 에이전트를 소환하고, 회의록을 정리한다.

**비판**:
- COS 자체가 토큰을 소비한다. 브리핑 생성, 안건 정리, 회의 중재, 기록 갱신 — 이 모든 것이 LLM 컨텍스트 윈도우를 차지한다.
- COS가 스스로 인정했다: "소환이 전부 반응적, 선제적 판단 없음". 그러면 COS는 단순 디스패처인데, 디스패처에 이 정도의 프로토콜 오버헤드가 필요한가?
- CLAUDE.md 창업 모드만 200줄이 넘는다. 이것 자체가 매 세션마다 시스템 프롬프트에 들어간다.

## 3. 1인 개발 리스크

### 3.1 비개발자의 기술 부채 [심각도: 치명적]

**문제**: 창업자가 비개발자다. "1년간 AI 도구 사용 경험"이 있지만, 소프트웨어 엔지니어링은 AI 도구 사용과 다르다.

**구체적 우려**:
- 36차에서 COS(Claude)가 직접 코드를 작성했다. Claude Code로 코드를 생성하는 것 자체는 가능하지만, **코드를 이해하고 디버깅하고 운영하는 역량**은 별개다.
- `ReadableStream try/catch` 같은 기본적인 에러 핸들링이 빠져 있다가 검증 에이전트가 잡았다. 이건 경험 있는 개발자라면 처음부터 넣는 패턴이다.
- Vercel 서버리스 + SSE 스트리밍 + Anthropic SDK + Next.js App Router — 이 조합의 엣지 케이스를 다루려면 상당한 실전 경험이 필요하다.

### 3.2 코드 품질 [심각도: 높음]

**문제**: 코드 리뷰를 하는 것이 AI 에이전트뿐이다.

**우려**:
- AI가 생성한 코드를 AI가 리뷰하는 구조. 같은 편향이 재생산된다.
- `types-v2.ts`에 ExpertName을 화이트리스트로 하드코딩했다. 전문가를 추가하려면 타입 파일을 수정해야 한다. 이것은 설정이 아니라 코드 변경이다.
- `expert-recommend.ts`에서 concern_type 9종을 하드코딩한 매핑. 새 유형 추가 시 코드 수정 필수. 설정 파일이나 DB로 분리하는 것이 기본인데 모든 것이 하드코딩이다.

### 3.3 보안 [심각도: 치명적]

**문제**: 인증이 없다.
- API 엔드포인트(`/api/chat`, `/api/analyze`, `/api/debate`)에 아무나 접근 가능하다.
- 누군가 스크립트로 `/api/analyze`를 무한 호출하면 API 비용이 폭발한다.
- rate limiting 코드가 보이지 않는다.
- API 키가 서버에서만 사용된다고 해도, 클라이언트에서 직접 호출되는 구조가 아닌지 확인이 필요하다.

### 3.4 인프라 운영 역량 [심각도: 높음]

**문제**: Vercel에 배포했지만, 모니터링/로깅/알림이 없다.
- API 호출 실패율을 모른다.
- 사용자가 얼마나 쓰는지 모른다 (DB 없으니까).
- 비용이 얼마나 나가는지 실시간으로 모른다.
- 장애가 나면 어떻게 아나? Vercel 대시보드를 계속 쳐다보나?

## 4. 운영 효율성 비판

### 4.1 37차 세션의 산출물 대비 효율 [심각도: 높음]

**문제**: 37차 세션에서 나온 실제 코드 산출물은 **36~37차의 2개 세션**에서 만들어졌다.

**분석**:
- 1~35차: 사업계획서, PPT, 발표 대본, 검증, 회고 — **제품 코드 0줄**
- 36차: Claude API 전환 + 안전 레이어 (8개 파일)
- 37차: v2 엔드포인트 (8개 파일)
- **35/37 = 94.6%의 세션이 문서 작업**이었다.

물론 사업계획서가 필요했다. 하지만 35개 세션이 필요했나? PPT 검증에 극악 채점표를 만들고, 4팀 병렬 검증을 돌리고, 99.8% 달성을 목표로 한 것은 **완벽주의의 함정**이다. 신청서는 통과하면 되는 것이지, 100점을 받을 필요가 없다.

### 4.2 파일 기반 상태 관리의 한계 [심각도: 중간]

**문제**: team_state.yaml + 대시보드.md + 세션_맥락.md로 상태를 관리한다.

**비판**:
- YAML 파일이 "진실의 원천(source of truth)"인데, 이걸 수동으로 갱신한다. 갱신이 누락되면 다음 세션에서 COS가 잘못된 맥락으로 브리핑한다.
- 대시보드.md에 "Sprint 1 목표" 테이블이 있는데, 실제 진행 상황과 동기화가 안 맞는다. 예: "Claude API 연결 — 미착수"라고 되어 있지만, 바로 아래 37차 완료 사항에 "완료"라고 적혀 있다.
- 이 모든 것이 **사람이 읽으라고 만든 문서인데, 실제 독자가 AI**다. AI에게 최적화된 구조화 포맷(JSON, 구조화 스키마)이 아니라 마크다운 산문이다.

### 4.3 세션 간 컨텍스트 손실 [심각도: 높음]

**문제**: Claude Code 세션은 컨텍스트 윈도우가 유한하다. 37차까지 진행했다는 것은 최소 37번의 세션 전환이 있었다는 뜻이다.

**결과**:
- 세션_맥락.md에 "다음 세션 할 일"이 있지만, 이전 세션의 **미묘한 논의 맥락**은 전달되지 않는다.
- 역발상 보고서에서 스스로 인정: "컨텍스트를 AI에게 맡기면 컨텍스트가 소실된다."
- 팀원 프롬프트에 "불변 정보만" 담고 "세션별 맥락은 소환 시 COS가 전달"한다고 하는데, COS 자체가 새 세션에서 맥락을 완전히 복원하지 못한다.

## 5. 안전 시스템 비판

### 5.1 키워드 기반 위기 감지의 한계 [심각도: 치명적]

**문제**: `crisis-keywords.ts`에 Tier A 45개 + Tier B 22개를 하드코딩했다.

**근본적 결함**:
- **우회가 너무 쉽다.** 공백 삽입 우회는 `replace(/\s+/g, "")` 정규화로 방어했지만:
  - 동의어/은유: "세상을 떠나고 싶다", "이 모든 게 끝났으면", "잠들어서 안 깨면 좋겠다" — 키워드에 없으면 놓친다.
  - 자소 분리: "ㅈㅜㄱ고 싶다" — 정규화가 잡지 못한다.
  - 맥락 의존: "죽이고 싶은 맛"은 음식 이야기인데, 단순 매칭이면 Tier A로 분류한다.
- **False positive**: 요리("죽 끓이다"), 게임("죽었다"), 비유("죽을 만큼 바쁘다")에서 오발동할 수 있다.
- **False negative이 더 위험하다.** 실제로 위험한 사용자가 키워드를 사용하지 않으면 전혀 감지하지 못한다.

**업계 기준**: Woebot, Wysa 등은 키워드 + **문맥 이해 NLP 모델(별도 classifier)** + **사용자 행동 패턴(세션 빈도, 감정 추이)** 조합으로 위기를 감지한다. 키워드만으로는 안전하다고 주장할 수 없다.

### 5.2 법적 리스크 [심각도: 치명적]

**문제**: 면책 구조가 없다.

**구체적 우려**:
- 이용약관(Terms of Service) 미작성
- 면책 조항(Disclaimer) 미구현
- 개인정보처리방침 미작성 (KPIPA 의무 사항)
- "웰니스/코칭으로 포지셔닝 (규제 회피)"라고 했는데, **포지셔닝만으로 규제를 회피할 수 없다.** 실제 서비스 내용이 "멘탈케어"이고 사용자가 정신건강 관련 상담을 하면, 정신건강복지법상 문제가 될 수 있다.
- 사용자가 서비스 이용 중 자해/자살 시도를 했고, Tier A 감지가 실패했다면? **법적 책임 소재가 불명확하다.**
- 최소한 매 세션 시작 시 "이 서비스는 전문 상담을 대체하지 않습니다" 동의 팝업이 필요하고, 이것의 법적 효력도 별도 검토가 필요하다.

### 5.3 안전 레이어가 후반에 끼워맞춰짐 [심각도: 높음]

**문제**: Domain Expert 에이전트가 스스로 인정했다: "안전이 후반에 끼워맞춰짐."

**근거**:
- v1에서 chat API에 위기 감지가 0%였다. route-concern에만 있었고, 세션 진행 중 위기 발언은 아무 대응이 없었다.
- 36차에서야 chat API에 안전 체크가 들어갔다. **35차 세션 동안 안전 없이 서비스가 배포되어 있었다** (pullim.vercel.app).
- Gemini 기반 v1이 실제로 외부에 노출된 상태에서 위기 감지 없이 운영된 것은 **이미 사고가 날 수 있었던 상태**다.

## 6. 예산 현실성 비판

### 6.1 425만원의 한계 [심각도: 높음]

**내역**: Claude Max 145만 + LLM API 100만 + 서버 50만 + 테스트 30만 + UI/UX 100만

**비판**:

| 항목 | 배정 | 현실 |
|------|------|------|
| Claude Max 145만원 | 개발용 Claude Code 구독 | 이것은 **운영비가 아니라 개발 도구 비용**. 제품 API 비용과 별도. 6개월이면 870만원 |
| LLM API 100만원 | 제품 API 비용 | v2 기준 세션당 543원. 100만원 / 543원 = **1,841세션**. 유저 100명이 월 4회 쓰면 2.6개월이면 소진 |
| 서버 50만원 | Vercel + Supabase | Vercel Pro 월 $20, Supabase Free로 시작하면 넉넉해 보이지만, 함수 실행 시간 초과 시 Enterprise 필요 |
| 테스트 30만원 | 사용자 테스트 비용 | Solution Interview 5명이 목표인데, 30만원이면 인당 6만원. 적정 |
| UI/UX 100만원 | 외주 디자인 | 100만원으로 살 수 있는 UI/UX의 품질은 제한적. 템플릿 커스터마이징 수준 |

**핵심**: 425만원은 **3~4개월 운영비**다. 그 안에 Product-Market Fit을 찾지 못하면 끝이다. 그런데 현재 MVP조차 미완성이고, Solution Interview도 0건이다.

### 6.2 API 비용 burn rate [심각도: 높음]

**문제**: v2 세션당 543원은 "보수적 추정의 상한선"이라고 했는데, 이전 CTO 분석에서 Sonnet 기준 198원이었다가 Opus 하이브리드로 전환하면서 2.7배 뛰었다.

- 실측 데이터가 없다. 543원은 추정치다.
- thinking tokens을 쓰면 더 올라간다.
- 사용자가 추가 질문을 하거나 토론이 길어지면 더 올라간다.
- **유료 전환 전까지 모든 API 비용은 순손실이다.**

### 6.3 수익 없는 상태의 지속 가능성 [심각도: 높음]

**현실**:
- 현재 수익: 0원
- 결제 시스템: 미구현
- 유료 전환 예상 시점: MVP 출시 후 (4월 이후?)
- 인증조차 없어서 유료 회원을 구분할 수 없다
- BEP 1명이라고 했는데, 그건 API 비용만 놓고 계산한 것이다. Claude Max 구독, 서버, 개발 시간의 기회비용은 빠져 있다.

## 7. 기술 모트(해자) 비판

### 7.1 "파이프라인"이 진짜 기술적 해자인가? [심각도: 치명적]

**주장**: "프롬프트가 아니라 파이프라인 — 상태 관리 + 오케스트레이션 + 안전 레이어"

**비판**:

이것은 해자가 아니다. 이유:

1. **복제 난이도가 낮다.** 현재 코드베이스는 Next.js + Anthropic SDK + 하드코딩된 프롬프트/키워드. 경험 있는 개발자 1명이 2주면 똑같이 만든다. 아니, 더 잘 만든다 (DB 포함해서).

2. **오케스트레이션 자체는 가치가 아니다.** API를 여러 번 호출하는 것은 누구나 할 수 있다. 가치는 **오케스트레이션의 결과물 품질**에서 나오는데, 이걸 측정한 적이 없다. "한 명도 실제로 안 써봄"이라고 했다.

3. **안전 레이어는 67개 키워드 하드코딩이다.** 이것은 해자가 아니라 최소한의 안전장치도 안 되는 수준이다.

### 7.2 데이터 축적 불가 현황 [심각도: 치명적]

**주장**: "[13차] 모트: 축적 데이터 록인 (개인 데이터 복제 불가)"

**현실**: DB가 없다. 데이터를 저장하지 않는다. 축적이 물리적으로 불가능하다.

**가정적 미래**: Supabase를 붙인다고 해도:
- 데이터 록인의 전제는 사용자가 **반복 사용**해야 한다. 현재 무료 1회로는 록인이 형성되지 않는다.
- 경쟁자가 "데이터 이동권"을 내세우면 록인은 무력화된다. EU GDPR, 한국 개인정보보호법 모두 데이터 이동권을 보장한다.
- 멘탈케어 데이터는 **민감 정보**다. 축적할수록 보안/프라이버시 부담이 커진다. 이 비용을 425만원 예산에서 감당할 수 있나?

### 7.3 실제 해자 후보 — 있긴 한가? [심각도: 참고]

솔직히 말하면, 현 단계에서 기술 해자를 논하는 것 자체가 시기상조다. 해자는 PMF를 찾은 다음에 만드는 것이다. 지금은:
- 사용자 5명이 써보고 "다시 쓰겠다"라고 했는가? (안 했다)
- 유료로 내겠다고 한 사람이 있는가? (대표 테스트: "유료면 안 씀")
- 경쟁 제품 대비 확실히 나은 점이 있는가? (검증 안 됨)

## 결론

풀림팀은 **제품을 만들기 전에 회사를 만들었다.** COS, 에이전트 팀, 회의 릴레이, 크로스체크 프로토콜 — 이 모든 것이 "제품이 좋으면 의미 있는" 시스템이다. 그런데 제품이 아직 없다. DB 없이 배포된 프론트엔드 미연동 백엔드가 있을 뿐이다.

37차 세션의 95%가 문서 작업이었다는 사실이 모든 것을 말해준다. 에이전트 팀이 만든 것은 문서이고, 사용자가 필요한 것은 동작하는 제품이다.

**즉시 해야 할 3가지**:
1. 에이전트 팀 회의를 중단하고, **코드를 짜라.** DB 붙이고, 인증 넣고, 프론트 연동해라.
2. Opus x3를 **Sonnet x3으로 다운그레이드**하고 실측해라. 품질 차이가 유료 전환을 결정할 만큼 큰지 먼저 확인해라.
3. 5명한테 써보게 해라. **지금 당장.** 면책 팝업 하나 넣고, 지인 5명한테 URL 보내라. 극악 채점표 99.8%보다 사용자 피드백 5건이 만 배 가치 있다.
