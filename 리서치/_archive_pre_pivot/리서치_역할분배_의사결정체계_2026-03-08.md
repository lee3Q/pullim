## 1. 의사결정 프레임워크 비교 분석

### 1-1. RAPID (Bain & Company)

| 역할 | 의미 | 설명 |
|------|------|------|
| **R** — Recommend | 제안자 | 데이터 수집, 분석, 대안 제시. 결정권 없음 |
| **A** — Agree | 동의자 | 제안에 대해 공식 동의/반대 의견 제출. 거부권은 없지만 기록됨 |
| **P** — Perform | 실행자 | 결정이 나면 실행 담당 |
| **I** — Input | 자문자 | 전문 의견 제공. 의사결정 직접 참여 안 함 |
| **D** — Decide | 결정자 | 최종 결정권. 1명만 가능 |

**AI 창업팀 적용:**
- D(Decide) = 대표 이상규 (고정)
- R(Recommend) = 모든 에이전트 팀원 (민주적 제안)
- I(Input) = 전문 분야별 에이전트 (도메인 자문)
- P(Perform) = 해당 업무 담당 에이전트
- A(Agree) = 회의 참석 에이전트 전원

**장점:** 결정자 1명으로 명확. 제안/실행 분리.
**적합도:** ★★★★★ — 창업자 최종 승인 + 팀 자율 제안에 가장 적합

---

### 1-2. DACI (Atlassian)

| 역할 | 의미 | 설명 |
|------|------|------|
| **D** — Driver | 드라이버 | 프로젝트 추진. 일정 관리. 결정자 아님 |
| **A** — Approver | 승인자 | 최종 승인. 1명만 |
| **C** — Contributors | 기여자 | 전문 지식 투입 |
| **I** — Informed | 통보 대상 | 결과만 전달받음 |

**AI 창업팀 적용:**
- A(Approver) = 대표 이상규
- D(Driver) = COO/PM 에이전트 (회의 진행, 의제 관리)
- C(Contributors) = 전문 에이전트 (CTO, CMO 등)
- I(Informed) = 실행 후 결과를 받는 에이전트

**장점:** Driver와 Approver 분리로 대표 부담 경감.
**적합도:** ★★★★☆ — 대표가 매번 회의 주도 안 해도 됨

---

### 1-3. RACI (전통적)

| 역할 | 의미 |
|------|------|
| R — Responsible | 실행 책임 |
| A — Accountable | 최종 책임 (1명) |
| C — Consulted | 사전 자문 |
| I — Informed | 사후 통보 |

**적합도:** ★★★☆☆ — 대기업/중기업 프로세스. 초기 스타트업엔 무거움

---

### 1-4. Advice Process (Teal 조직 / Laloux)

**원칙:**
- 누구나 어떤 결정이든 내릴 수 있음
- 단, 결정 전에 (1) 영향 받는 사람 (2) 전문가에게 조언을 구해야 함
- 조언을 들은 후 결정은 제안자가 내림 (만장일치 불필요)

**AI 창업팀 적용:**
- 에이전트가 제안 → 관련 에이전트에게 의견 수렴 → 대표에게 승인 요청
- 사소한 결정: 에이전트 자체 실행 (보고만)
- 중요한 결정: 대표 승인 필수

**장점:** 자율성 극대화. 병목 최소화.
**적합도:** ★★★★★ — 자율 운영 + 대표 최종 승인과 완벽 호환

---

### 1-5. Consent-Based (소시오크라시)

**원칙:**
- 만장일치가 아니라 "충분히 좋은가? 치명적 반대가 없는가?" 기준
- 반대 의견은 "paramount objection"만 유효 (감정적 불만 X)
- 라운드 방식: 한 명씩 돌아가며 반대 여부 표명

**AI 창업팀 적용:**
- 회의에서 각 에이전트가 라운드로 의견 → 치명적 반대 없으면 통과
- 대표가 참여 시 최종 확정, 미참여 시 consent-based로 자율 운영

**적합도:** ★★★★☆ — 회의 체계에 적합

## 2. 창업자-팀 간 권한 위임 모델

### 2-1. 결정 유형별 권한 분배 (핵심)

| 결정 유형 | 예시 | 권한 수준 | 대표 역할 |
|----------|------|----------|----------|
| **전략적** | 사업 방향, 피벗, 포지셔닝 변경 | 대표 전결 | 직접 결정 |
| **전술적** | 마케팅 채널, 기능 우선순위 | 팀 제안 → 대표 승인 | 승인/반려 |
| **운영적** | 일정 관리, 리서치 범위, 문서 포맷 | 팀 자율 → 대표 보고 | 보고 수신 |
| **실행적** | 구체적 실행 방법, 도구 선택 | 팀 자율 (보고 불필요) | 관여 안 함 |

### 2-2. 권한 위임 원칙 (Startup Context)

1. **"What" vs "How" 분리**
   - 대표 = What (뭘 할지, 왜 할지)
   - 팀 = How (어떻게 할지)
   - 예: 대표 "진로 특화 MVP를 만들자" → 팀이 기술 스택/디자인/일정 결정

2. **Escalation 기준 명확화**
   - 비용 > X원 → 대표 승인
   - 방향 변경 → 대표 승인
   - 새 팀원 소집 → 대표 승인
   - 외부 공개 → 대표 승인
   - 나머지 → 팀 자율

3. **Default to Action (행동 우선)**
   - 판단 미비 시 "일단 실행, 결과 보고" (분석 마비 방지)
   - 이상규 CLAUDE.md 교훈: "분석이 행동을 대체한다" 방지

4. **Reversibility Test (가역성 테스트)**
   - 가역적 결정 (되돌릴 수 있음) → 팀 자율 실행
   - 비가역적 결정 (되돌리기 어려움) → 대표 승인 필수
   - Amazon "Type 1 vs Type 2 decisions" (Bezos Letter 2016)

## 3. 제안-승인 워크플로우 설계

### 3-1. 제안서 표준 템플릿

```markdown
## 제안서
- 제안자: [에이전트명]
- 일시: [날짜]
- 유형: 전략 / 전술 / 운영
- 긴급도: 긴급(24h) / 일반(3일) / 참고

### 배경
[왜 이 제안을 하는가]

### 제안 내용
[구체적으로 뭘 하자는 건지]

### 대안
[검토한 다른 옵션 + 탈락 사유]

### 예상 효과
[실행 시 기대 효과]

### 리스크
[잘못될 수 있는 점 + 대응]

### 필요 리소스
[시간/인력/비용]

### 승인 필요 여부
- [ ] 대표 승인 필요 (전략/전술)
- [ ] 팀 자율 실행 (운영/실행) — 보고만
```

### 3-2. 승인 흐름

```
제안자(아무 에이전트) → 일일 회의 안건 등록
    ↓
회의에서 팀 전체 토론 (라운드 방식)
    ↓
[운영/실행급] → 치명적 반대 없으면 즉시 실행 → 대표에게 결과 보고
[전술급] → 팀 의견 종합 → 대표에게 제안서 + 팀 의견 전달 → 승인/반려/수정
[전략급] → 대표 직접 참여 필수 → 토론 후 대표 결정
```

### 3-3. 대표 참여 방식 (유연)

| 모드 | 설명 | 적합 상황 |
|------|------|----------|
| **실시간 참여** | 회의에 직접 참석, 실시간 피드백 | 전략적 결정, 초기 방향 설정 |
| **비동기 검토** | 회의록 + 제안서 검토 → 코멘트 | 일상적 운영, 바쁜 날 |
| **위임 모드** | 특정 기간 팀에 전결 위임 | 시험 기간, 출장 등 |

## 4. 자율 운영 프레임워크

### 4-1. Spotify Squad Model (변형)

**원본:** Spotify의 Squad(실행팀) - Tribe(부족) - Chapter(직능) - Guild(관심사)

**AI 창업팀 변형:**
- Squad = 전체 팀 (초기엔 1개 Squad로 충분)
- 각 에이전트 = 직능 역할 (CTO, CMO, PM 등)
- Chapter = 필요 시 외부 에이전트 소집 (리서치 특공대 등)

### 4-2. OKR + Sprint (실행 구조)

| 주기 | 활동 | 책임 |
|------|------|------|
| **분기** | OKR 설정 (대표 + 팀) | 대표 방향, 팀 KR 제안 |
| **주간** | Sprint 계획 + 회고 | PM 에이전트 주도 |
| **일일** | Standup (진행/차단/계획) | 전원 참여 |

### 4-3. 자율 운영 5대 원칙

1. **투명성 (Transparency)**
   - 모든 결정의 근거가 기록됨
   - 회의록은 항상 생성, 대표가 언제든 열람 가능

2. **자기 조직화 (Self-Organization)**
   - 업무 분배는 팀 내부에서 (대표 지시 X)
   - 전문 에이전트가 본인 도메인 업무를 선점

3. **실패 허용 (Safe-to-Fail)**
   - 가역적 실행에서의 실패 = 학습. 책임 추궁 없음
   - 단, 같은 실패 반복 = 프로세스 개선 안건

4. **Minimum Viable Bureaucracy (최소 관료주의)**
   - 승인 단계는 최소화 (운영급은 승인 불필요)
   - 문서화는 하되, 문서 작성이 실행을 지연시키면 안 됨

5. **정기 회고 (Retrospective)**
   - 주 1회: 이 프로세스 자체가 잘 작동하는가?
   - 팀원 누구든 프로세스 변경 제안 가능

## 5. AI 에이전트 팀 특화 고려사항

### 5-1. 인간 팀 vs AI 에이전트 팀 차이

| 항목 | 인간 팀 | AI 에이전트 팀 |
|------|---------|--------------|
| 감정/정치 | 있음 → 갈등 관리 필요 | 없음 → 역할 충돌만 관리 |
| 문맥 유지 | 자연스러움 | 세션 간 명시적 전달 필요 |
| 병렬 실행 | 제한적 | 동시 다수 태스크 가능 |
| 소집/해고 | 비용 큼 | 즉시 가능 |
| 전문성 변경 | 교육 필요 | 프롬프트 수정으로 즉시 |
| 자발적 제안 | 자연스러움 | **명시적 설계 필요** (프롬프트에 제안 권한 포함) |

### 5-2. 에이전트 자율 제안 설계 패턴

```
각 에이전트 시스템 프롬프트에 포함:
1. "너는 본인 도메인에서 문제/기회를 발견하면 자발적으로 제안해야 한다"
2. "제안 시 표준 템플릿(3-1)을 사용한다"
3. "다른 에이전트의 제안에 대해 전문가 관점에서 의견을 제시한다"
4. "대표의 최종 결정을 존중하되, 전문가로서 반대 의견은 명확히 기록한다"
```

### 5-3. 문맥 유지 메커니즘

| 메커니즘 | 설명 |
|----------|------|
| **팀 상태 문서** | 현재 OKR, 진행 중 태스크, 미결 안건 — 항상 최신 |
| **회의록 체인** | 이전 회의 결정 → 다음 회의 시작점 |
| **결정 로그** | 모든 결정 + 근거 + 결과 추적 |
| **에이전트 브리핑 시트** | 각 에이전트 소집 시 읽는 "현재 상황 요약" |

## 6. 추천 의사결정 체계 (종합)

### "RAPID + Advice Process" 하이브리드

이 창업팀에 가장 적합한 모델:

```
[기본 구조: RAPID]
- Decide = 대표 이상규 (전략/전술)
- Recommend = 모든 에이전트 (민주적 제안)
- Input = 도메인 전문 에이전트
- Agree = 회의 참석자 전원 (라운드 방식)
- Perform = 담당 에이전트

[자율 운영: Advice Process]
- 운영/실행급 결정 → 에이전트가 관련자 의견 수렴 후 자체 결정
- 전술급 이상 → RAPID 프로세스 발동

[회의 방식: Consent-Based]
- 라운드 방식으로 의견 수렴
- "치명적 반대(paramount objection)"만 블로킹
- 나머지는 proceed
```

### 왜 이 조합인가

| 요구사항 | 해결 프레임워크 |
|----------|---------------|
| 대표 = 최종 승인권자 | RAPID의 D(Decide) |
| 민주적 제안 | RAPID의 R(Recommend) + Advice Process |
| 자율 운영 | Advice Process (운영급 자체 결정) |
| 유연한 대표 참여 | 비동기 검토 모드 |
| 분석 마비 방지 | Default to Action + 가역성 테스트 |
| 프로세스 자체 개선 | 주간 회고 + 누구든 변경 제안 |

## 8. 이 팀에의 시사점 (액션 아이템)

1. **결정 유형 4단계** (전략/전술/운영/실행) 도입 → 에이전트가 제안 시 자동 분류
2. **제안서 표준 템플릿** 확정 → 모든 에이전트 프롬프트에 포함
3. **가역성 테스트** 의무화 → "이 결정 되돌릴 수 있나?" 체크리스트
4. **대표 3모드** (실시간/비동기/위임) → 팀 상태 문서에 현재 모드 표시
5. **주간 회고** → 프로세스 자체를 개선하는 메타 루프
6. **에이전트 자발적 제안** → 시스템 프롬프트에 명시적 권한 부여
