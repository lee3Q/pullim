## 1. 창업/경영 방법론 프레임워크 분석

### 1-1. Lean Startup (Eric Ries)
| 원칙 | 적용 |
|------|------|
| Build-Measure-Learn 루프 | MVP → 사용자 피드백 → 개선의 반복. 완벽한 제품이 아니라 학습 속도가 핵심 |
| Minimum Viable Product | 이미 PRD v1 + seed.yaml 있음. Claude 기반 프로토타입으로 빠르게 검증 |
| Pivot or Persevere | 포지셔닝 이미 1차 피벗 완료 (진로특화 → 멘탈케어 하이브리드) |
| Validated Learning | 가설 4개 설정됨. 수동 Socratic 테스트 필요 |
| **팀 시사점** | 초기엔 "만드는 사람 + 파는 사람 + 측정하는 사람" 3명이면 충분 |

### 1-2. Customer Development (Steve Blank)
| 단계 | 현재 위치 | 필요 역할 |
|------|-----------|-----------|
| Customer Discovery | ✅ 진행 중 (인터뷰 3건 완료) | 리서치/인터뷰 담당 |
| Customer Validation | ⬜ 다음 단계 | MVP + 초기 사용자 확보 담당 |
| Customer Creation | ⬜ | 마케팅/그로스 담당 |
| Company Building | ⬜ | 조직 운영 담당 |
| **팀 시사점** | Discovery/Validation 단계에서는 빌더+허슬러 2-3명이 최적. 대규모 팀은 오히려 방해 |

### 1-3. Y Combinator 모델
| 원칙 | 내용 |
|------|------|
| 최적 창업팀 사이즈 | **2-3명**. YC 역사상 가장 성공한 팀은 대부분 2명 (Airbnb, Stripe, Dropbox) |
| 필수 역할 | "Hacker + Hustler" 또는 "Hacker + Hustler + Designer" |
| 초기 집중 | "Do things that don't scale" — 자동화보다 수동으로 고객 확보/서비스 제공 |
| 팀 추가 타이밍 | Product-Market Fit 이전에 팀 확장하면 위험. "빠르게 만들고 빠르게 배우는" 능력 저하 |
| **팀 시사점** | 핵심 기능을 직접 만들 수 있는 빌더 1명 + 고객/시장을 이해하는 사람 1명이 최소 단위 |

### 1-4. Amazon의 Two-Pizza Team
| 원칙 | 적용 |
|------|------|
| 피자 2판으로 먹일 수 있는 팀 사이즈 | **5-8명 이하** |
| 자율성 | 팀이 외부 의존 없이 독립적으로 의사결정하고 실행할 수 있어야 함 |
| 커뮤니케이션 비용 | n명 팀의 소통 채널 = n(n-1)/2. 5명=10채널, 10명=45채널 |
| **팀 시사점** | AI 에이전트 팀도 동일하게 적용. 에이전트 과다 소집 = 토큰 낭비 + 의견 분산 |

### 1-5. Spotify Squad 모델
| 원칙 | 적용 |
|------|------|
| Squad | 자율적 미니 팀 (4-8명), 하나의 미션에 집중 |
| Tribe | 관련 Squad들의 집합 |
| Chapter | 같은 전문 분야 크로스 Squad |
| **팀 시사점** | 초기엔 Squad 1개만. 스케일업 시 모델로 전환 가능 |

## 2. 초기 스타트업 핵심 역할 정의

### 2-1. 보편적 스타트업 핵심 역할 (단계별)

#### Pre-Seed / Discovery 단계 (← 현재 위치)
| 역할 | 필수 여부 | 핵심 책임 |
|------|-----------|-----------|
| **CEO / 비전 설정자** | ✅ 필수 | 방향 설정, 최종 의사결정, 대외 대표 |
| **CTO / 빌더** | ✅ 필수 | MVP 개발, 기술 아키텍처, 프로토타입 |
| **Product Manager** | ⚠️ 권장 | 사용자 리서치, 기능 우선순위, 로드맵 |
| 디자이너 | 선택 | UI/UX, 브랜딩 (초기에는 CEO/PM이 겸임 가능) |
| 마케터 | 선택 | 초기에는 CEO가 직접 수행 (Do things that don't scale) |

#### Seed / Validation 단계
| 역할 | 필수 여부 | 핵심 책임 |
|------|-----------|-----------|
| CEO | ✅ | + 투자 유치, 팀 빌딩 |
| CTO | ✅ | + 기술 부채 관리, 스케일링 준비 |
| PM | ✅ | + 데이터 분석, A/B 테스트 |
| **마케터 / 그로스** | ✅ 필수로 승격 | 유저 획득, 리텐션, 바이럴 |
| **디자이너** | ✅ 필수로 승격 | 제품 경험 차별화 |

### 2-2. AI 스타트업 특화 역할

AI 제품 스타트업은 전통 SaaS와 다른 역할이 필요:

| AI 특화 역할 | 책임 | 이 사업에서의 필요성 |
|-------------|------|---------------------|
| **프롬프트 엔지니어 / AI 아키텍트** | LLM 프롬프트 설계, 파이프라인 최적화, 모델 선택 | ✅ 핵심. 7단계 Socratic 파이프라인 품질 = 제품 품질 |
| **AI 안전/윤리 담당** | 위기 감지, 편향 관리, 면책 구조 | ⚠️ 중요. 멘탈케어 포지셔닝에서 안전 = 생사 |
| **데이터 전략가** | 사용자 데이터 수집/분석, 패턴 학습 설계 | 선택 (v2에서 필요) |
| **도메인 전문가** | 심리/상담/의사결정 이론 전문성 | ⚠️ 중요. 프레임워크 선택과 질문 품질에 직결 |

## 3. AI 에이전트 팀으로의 전환 — 모범사례

### 3-1. 에이전트 팀 ≠ 인간 팀 (핵심 차이)

| 차원 | 인간 팀 | AI 에이전트 팀 |
|------|---------|---------------|
| 커뮤니케이션 비용 | 높음 (회의/미팅) | 낮음 (텍스트 전달) |
| 전문성 전환 | 불가 (채용/해고) | 즉시 (프롬프트 교체) |
| 동시 작업 | 물리적 제한 | 병렬 실행 가능 |
| 맥락 유지 | 인간 기억 + 문서 | 파일 시스템 기반 상태 저장 |
| 리스크 | 퇴사, 갈등 | 프롬프트 오염, 토큰 한도 |
| 비용 구조 | 고정비 (월급) | 변동비 (토큰) |

### 3-2. AI 에이전트 팀 설계 원칙

1. **최소 인원 원칙**: 인간 팀보다 더 적어야 함. 에이전트 1명 = 인간 1명의 여러 역할 수행 가능
2. **전문성 분리 원칙**: 하나의 에이전트에 너무 많은 역할을 주면 프롬프트 오염 → 전문성 깊이 저하
3. **파일 기반 상태 관리**: 매 세션 시작 시 상태 파일을 읽어 맥락 복원
4. **회의 = 구조화된 프롬프트**: 자유 토론이 아닌 안건→분석→제안→승인 구조
5. **대표 = 라우터**: 모든 에이전트의 출력을 종합하고 최종 결정하는 역할

### 3-3. 이 사업의 최소 에이전트 팀 구성 제안

#### 방안 A: 최소 3명 (린 모델)
```
대표 (이상규) — 비전, 방향, 최종 승인
   ├── CTO/빌더 에이전트 — MVP 개발 + 프롬프트 엔지니어링
   ├── PM/전략 에이전트 — 제품 전략 + 사용자 리서치 + 시장 분석
   └── 도메인 전문가 에이전트 — 심리학/의사결정 이론 + AI 안전
```
- **장점**: 토큰 효율, 빠른 의사결정, 소통 채널 3개뿐
- **단점**: 역할 과중, 전문성 깊이 제한

#### 방안 B: 5명 (균형 모델) ⭐ 권장
```
대표 (이상규) — 비전, 방향, 최종 승인
   ├── CTO 에이전트 — 기술 아키텍처, MVP 개발, 배포
   ├── 프롬프트/AI 에이전트 — Socratic 파이프라인 설계, LLM 최적화
   ├── PM/전략 에이전트 — 제품 로드맵, 사용자 리서치, 경쟁 분석
   ├── 마케팅/그로스 에이전트 — 포지셔닝, 유저 획득, 콘텐츠 전략
   └── 도메인 전문가 에이전트 — 심리학/상담학/의사결정 이론, 안전 기준
```
- **장점**: 각 역할이 명확, 전문성 깊이 확보, Two-Pizza 규모
- **단점**: 회의 시 토큰 소비 증가
- **권장 이유**: 이 사업은 "프롬프트 품질"과 "도메인 전문성"이 핵심 차별화 → 분리 필수

#### 방안 C: 7명 (풀 모델)
```
대표 (이상규)
   ├── CTO — 기술
   ├── AI 엔지니어 — 프롬프트/파이프라인
   ├── PM — 제품
   ├── 마케팅 — 그로스
   ├── 도메인 전문가 — 심리학/의사결정
   ├── 디자이너 — UX/UI/브랜딩
   └── 비즈니스/재무 — 수익 모델, 투자, 정부 지원금
```
- **장점**: 모든 영역 커버
- **단점**: Pre-Seed 단계에서 과잉. 커뮤니케이션 21채널. 토큰 낭비
- **판단**: PMF 이후 스케일업 시 적용

## 5. 스타트업 팀 구성 실패 패턴 (회피 목록)

| 실패 패턴 | 설명 | 우리 사업 적용 |
|-----------|------|---------------|
| **역할 겹침** | 여러 사람이 같은 결정을 내리려 함 → 갈등 | 에이전트 간 책임 경계 명확히 정의 |
| **스킬 갭 무시** | 필요한 역할이 빠진 채 진행 | 도메인 전문가 없이 멘탈케어 포지셔닝 = 위험 |
| **조기 과확장** | PMF 전에 팀 키움 → 번 레이트 증가 | 에이전트는 비용이 낮지만 토큰/복잡성 증가 |
| **빌더 부재** | 전략만 있고 실행 없음 | CTO 에이전트의 "코드 작성" 능력이 핵심 |
| **단일 관점** | 모든 에이전트가 비슷한 결론 → 에코 챔버 | 도메인 전문가의 "안전 우선" 관점이 균형추 |

## 6. 성공한 AI 스타트업 초기 팀 사례

### 6-1. Perplexity AI (2022~)
- **초기 팀**: 4명 (CEO, CTO, 2 엔지니어)
- **특징**: 전원 기술 인력. "만드는 능력"에 올인
- **교훈**: AI 제품은 프롬프트/모델 품질이 곧 제품. 기술팀 비중 높아야

### 6-2. Replika (2017~)
- **초기 팀**: CEO (비기술) + CTO + AI 연구원 + 심리학 고문
- **특징**: 감정 AI는 **도메인 전문가(심리학) 필수**
- **교훈**: 멘탈케어/감정 영역 = 전문가 없으면 제품 신뢰도 0

### 6-3. Noom (2008~, 현재 $1B ARR)
- **초기 팀**: CEO + CTO + 행동심리학 PhD
- **특징**: 기술 + 도메인(행동심리학) 결합이 핵심 해자
- **교훈**: 코칭/헬스케어 앱에서 도메인 전문성이 없으면 "또 다른 앱" 취급

### 6-4. 마인드카페 (한국, 2018~)
- **초기 팀**: 대표 + 개발자 + 상담심리 전공자
- **특징**: 한국 멘탈케어 시장에서 상담심리 전공자가 초기부터 참여
- **교훈**: 한국 시장에서도 도메인 전문가 초기 합류가 성공 패턴

## 7. 결론 및 권장사항

### 7-1. 최소 인원 구성
| 순위 | 역할 | 필요 근거 | 비고 |
|------|------|-----------|------|
| 1 | **대표 (이상규)** | 비전 설정, 최종 승인, 실 사용자 관점 | 이미 확정 |
| 2 | **CTO/빌더** | MVP 없으면 사업 없음. Next.js+Supabase 구현 | 에이전트 |
| 3 | **프롬프트/AI 엔지니어** | 제품 = 프롬프트 품질. Socratic 파이프라인이 핵심 차별화 | 에이전트 |
| 4 | **PM/전략가** | 사용자 리서치, 로드맵, "만들면 안 되는 것" 필터링 | 에이전트 |
| 5 | **도메인 전문가** | 멘탈케어 포지셔닝 + 안전 기준. 없으면 신뢰도/안전 리스크 | 에이전트 |

### 7-2. 마케팅 역할은?
- **즉시 소집하지 않아도 됨**. Customer Discovery 단계에서는 대표 + PM이 직접 수행
- **소집 시기**: MVP 출시 직전 (Validation 단계 진입 시)
- 단, 포지셔닝 메시지("감정 정리하러 왔는데 결정까지 됐다")는 이미 확정 → PM이 유지

### 7-3. 추가 인력 소집 트리거 (자율 제안 기반)
| 트리거 | 소집 역할 |
|--------|-----------|
| MVP 출시 2주 전 | 마케팅/그로스 에이전트 |
| 디자인 피드백 3건 이상 | UX/UI 디자이너 에이전트 |
| 투자/지원금 신청 시 | 비즈니스/재무 에이전트 |
| 법적 이슈 발생 시 | 법률 자문 에이전트 (ad-hoc) |
| 사용자 데이터 100건 이상 | 데이터 분석 에이전트 |

### 7-4. AI 스타트업 특화 조직 구조

```
┌─────────────────────────────────────────────┐
│              대표 (이상규)                    │
│   비전/방향/최종승인/실사용자 관점              │
│   + 대외 대표 (창업동아리, 발표)               │
└─────────┬───────────────────────────────────┘
          │
    ┌─────┼─────────────┬──────────────┐
    │     │             │              │
┌───▼──┐ ┌▼──────────┐ ┌▼───────────┐ ┌▼──────────────┐
│ CTO  │ │프롬프트/AI │ │ PM/전략    │ │도메인 전문가   │
│      │ │엔지니어    │ │            │ │(심리/의사결정) │
│기술  │ │파이프라인  │ │제품/시장   │ │안전/이론      │
│구현  │ │설계       │ │리서치      │ │프레임워크     │
└──────┘ └───────────┘ └────────────┘ └───────────────┘
   │          │              │              │
   └──────────┴──────────────┴──────────────┘
                    │
            ┌───────▼────────┐
            │  공유 파일 시스템  │
            │ (상태/회의록/결정) │
            └────────────────┘
```

### 7-5. 핵심 인사이트 3개

1. **"빌더 + 도메인 전문가" 조합이 AI 멘탈케어 스타트업의 생존 조건**
   - Replika, Noom, 마인드카페 모두 초기부터 도메인 전문가 포함
   - "의사결정 도우미"에서 도메인 전문가 없으면 Socratic 질문이 표면적 수준에 머뭄

2. **프롬프트 엔지니어를 CTO와 분리하라**
   - 이 사업에서 코드 품질과 프롬프트 품질은 다른 전문성
   - CTO가 프롬프트도 하면 둘 다 중간 수준에 머뭄

3. **4명 시작, 5명째는 팀이 스스로 제안**
   - 초기: 대표 + CTO + 프롬프트/AI + PM/전략 (4명)
   - 도메인 전문가는 PM이나 프롬프트 엔지니어가 "이건 전문가가 필요하다"고 제안했을 때 소집
   - → 이것이 "민주적 제안" 시스템의 첫 테스트 케이스
