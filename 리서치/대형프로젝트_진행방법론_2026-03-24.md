# 대형 프로젝트 진행 방법론 리서치 (3자 합성)

> 리서치일: 2026-03-24
> 소스: Claude (자체 웹서치) + Perplexity + Gemini Deep Research
> 태그: 대형프로젝트준비1

## 결론 요약

1인 + AI로 대형 프로젝트를 진행하는 최적 조합:

- **전략**: 린 스타트업 (가설 → 검증 루프)
- **실행**: Shape Up 3~4주 사이클 (Shaping 2~3일 → Building 2~3주 → Cooldown 2~3일)
- **구현**: Walking Skeleton (전체 파이프라인 얇게 관통) → Vertical Slice (한 번에 하나의 완전한 기능)
- **개인화 단계**: 규칙 기반 → 스코어링 → 컨텍스트 밴딧 (순차)
- **안전장치**: TDD 프롬프팅, 데이터-로직 분리, 초기 이벤트 10~25개 제한

## 프레임워크 비교

| 프레임워크 | 1인+AI 적합도 | 이유 |
|-----------|-------------|------|
| **Shape Up** | 높음 | 시간 고정 + 범위 유동. 1인이 scope 통제하기 좋음 |
| 린 스타트업 | 중간 | 가설 검증에는 최적이나, 구현 방법론은 약함 |
| Scrum | 낮음 | 팀 전제. 1인에게 오버헤드 |
| Design Sprint | 낮음 | 5일은 아키텍처 변경에 너무 짧음 |

→ **Shape Up(실행) + 린 스타트업(전략)** 조합이 정답

## Walking Skeleton + Vertical Slice

### Walking Skeleton이란
- 시스템의 주요 아키텍처를 모두 실제로 연결한 최소 end-to-end 구현
- 기능은 극히 단순해도 됨, 전체가 "진짜로 돌아가는" 것이 핵심

### 풀림 Walking Skeleton 예시
```
사용자 입력 → 행동 이벤트 수집(응답시간, 선택패턴) → DB 저장(events 테이블)
  → 다음 세션에서 이전 패턴 조회 → 규칙 기반으로 톤/접근 조정 → 응답
```

### Vertical Slice 순서 (예시)
1. Slice A: 기본 행동 이벤트 수집 + 저장
2. Slice B: 세션 간 데이터 조회 + 간단 통계
3. Slice C: 규칙 기반 개인화 v1 (이전 만족도 기반)
4. Slice D: 비언어적 신호 수집 (응답 시간, 선택 패턴)
5. Slice E: 감각 트리거 시스템 v1
6. ...

## 행동 분석 아키텍처 패턴

### 대형 서비스 공통 구조
```
이벤트 수집(클릭스트림) → 메시지 큐 → 저장소 → 배치/실시간 처리 → 모델 → 서빙 → 피드백 루프
```

### 풀림 축소형 아키텍처
```
프론트 SDK(이벤트 기록) → API 엔드포인트 → Supabase events 테이블
  → 배치 집계(사용자별 패턴) → 규칙 기반 개인화 → 프롬프트 주입
```

### 초기 추적 이벤트 (10~25개)
- `session_started`, `session_completed`
- `question_answered` (choice, response_time_ms)
- `crystal_selected` (crystal, selection_time_ms)
- `satisfaction_scored`
- `help_level_triggered` ("모르겠어" 횟수)
- `returning_user` (재방문)
- `message_length` (답변 길이 변화)
- `stage_skipped` / `stage_revisited`

## Cold Start 해결 전략

1. **Single-user Utility**: 개인화 없어도 가치 있는 도구여야 함 (의사결정 구조화, 세션 리포트)
2. **온보딩 설문**: 첫 세션에서 선호 질문 (고민 유형, 선호 포맷)
3. **인기 패턴 폴백**: 초기에는 "가장 만족도 높은 기본 세션 패턴" 추천
4. **수동 → 자동**: 초기엔 대표가 세션 로그 보고 수동 판단 → 골든 라벨 → 나중에 자동화

## 개인화 롤아웃 단계

| 단계 | 방법 | 필요 데이터량 |
|------|------|-------------|
| 1 | 규칙 기반 (if-else) | 세션 10+ |
| 2 | 스코어링/로지스틱 회귀 | 세션 100+ |
| 3 | 컨텍스트 밴딧 | 세션 1000+ |

## 안전장치

### 바이브 코딩의 함정 (Gemini 경고)
- AI 코딩 속도가 빠르면 아키텍처 경계가 무너지고 기술 부채가 누적됨
- **TDD 프롬프팅**: 코드 생성 전에 테스트를 먼저 정의
- **아키텍처 경계 강제**: 레이어 간 인터페이스를 명확히

### 데이터-로직 분리 원칙 (피벗 대비)
- LLM 프롬프트에 사용자 데이터/상태를 저장하지 않음
- 모든 사용자 데이터는 외부 DB에 명시적으로 저장
- 피벗 시: 데이터 자산 보존, 프롬프트/UI만 교체

### 비언어 수집 후보 기술 (추가 검증 필요)
- WebGazer: 브라우저 기반 시선 추적
- 키스트로크 다이내믹스: 타이핑 패턴 분석
- → 프라이버시 및 실용성 검증 필요

## 교차검증 결과 (2026-03-25, 3-model)

> 검증 모델: Claude Opus (메인) + Claude Sonnet (에이전트) + GLM-5
> 검증 대상: 위 리서치 결론 전체

### 3자 일치
- Walking Skeleton 접근 적합
- 밴딧은 데이터 충분 후 (당장 X)
- 초기 이벤트 수 제한 시작

### 리서치 결론 수정사항
1. **사이클 길이**: 3~4주 → **첫 2사이클 2주, 이후 3주로 조정 여부 판단**
2. **초기 이벤트**: 10~25개 → **5~10개** (3자 모두 축소 권장)
3. **스코어링 단계**: 필수 → **선택적** (규칙→바로 밴딧 가능, 데이터 패턴에 따라)
4. **신규 과제**: 프라이버시 설계 필요 (Opus 지적) + 고민라우팅 통합 경계 명확화 (Sonnet 지적)

### 분기점
- GLM-5만 Shape Up 자체를 부적합 판정 (칸반 하이브리드 권장)
- 반론: AI가 빌딩 담당하면 Shape Up 전제 성립 → 2/3 다수로 Shape Up 유지
