## 1. 현재 문제점 목록

### 심각도 A: 구조적 혼란 (지금 당장 해결 필요)

**A-1. 폴더/시스템 3중 분열**

- `창업/team/` — 영어 폴더. 독립된 CLAUDE.md + team_state.yaml + dashboard.md + agents/ + sprint_backlog.md. COO 정하린이 관리하는 별도 시스템.

**A-2. 팀원 구성 불일치**

| 위치 | 활성 팀원 | COO 포함? | 에이전트 프롬프트 위치 |
|------|----------|-----------|---------------------|
| `팀/` | CTO, AI Lead, PM, Domain (4명) | 보류 | `팀/prompts/` (4개 파일) |

`팀/컨설팅_분석_보고서.md`는 3명(CPO/CGO/CTO) 시작을 권고하는데, 실제 구성은 어디에도 이를 따르지 않음.

**A-3. CLAUDE.md가 참조하는 경로와 실제 구조 불일치**

- 어느 CLAUDE.md를 따라야 하는지 불분명

### 심각도 B: 설계상 문제

**B-1. 팀원 능동성 부재 (대표 비전과 가장 큰 괴리)**
- 현재 시스템: 대표가 "회의 시작" → 비서가 에이전트 소환 → 에이전트 발언 → 비서 정리
- 대표 비전: **팀원이 먼저 제안** → 대표 승인 → 실행
- 현재 CLAUDE.md에 팀원 능동성 메커니즘이 **전혀 없음**. 비서(Claude)만 능동적이고, 팀원은 소환되어야만 말할 수 있음.

**B-2. "비서" 역할의 한계**
- CLAUDE.md에서 Claude = 비서(Secretary). "의견 제시, 전문가 판단을 하지 않음."
- 하지만 실제로 비서가 안건 선정, 발언 순서 결정, 요약 판단 등 핵심 오케스트레이션을 모두 수행
- "비서"라는 이름과 실제 역할(팀 코디네이터/COS) 사이 간극
- 대표의 비전에서는 팀원이 "대표님, 이런 회의 돌려야 합니다"라고 먼저 제안하는데, 비서 모델에서는 불가능

**B-3. 에이전트 회의 비용 vs 가치**
- 에이전트 1명 소환 = Agent tool 1회 = Opus 레벨 서브에이전트 = 높은 토큰 비용
- 4명 순차 소환 + 2라운드 = 최소 8회 Agent call
- Customer Discovery 단계에서 이 비용이 정당화되는 안건이 드묾
- 대부분의 안건은 1-2명 의견이면 충분

**B-4. 코칭분석(03-07) 인사이트 미반영**
- 코칭심리학자의 분석: GROW 모델 적용, Landing 프로토콜, WANT 단계 추가, 우뇌적 요소
- 이 내용이 seed.yaml, PRD, 팀원 프롬프트 어디에도 반영 안 됨
- 팀원들이 이 분석의 존재를 모름 (참조 파일에 포함 안 됨)

**B-5. 옆 탭 에이전트 회의 메커니즘 부재**
- 대표 비전: 별도 Claude Code 탭에서 에이전트끼리 사전 토론 → 결과 파일 저장 → 메인 세션에서 참조
- 현재 CLAUDE.md: 이 메커니즘 자체가 설계되지 않음
- 파일 기반 정보 공유 프로토콜 없음

**B-6. AI 도구 활용 권고 시스템 부재**
- 대표 보유 도구: Gemini Pro, Perplexity Pro, Claude Code Max Plan
- 현재 시스템: 모든 작업을 Claude 안에서 처리
- 팀원이 "이 리서치는 Perplexity로 하세요"라고 권고하는 메커니즘 없음

## 3. 창업 모드 핵심 설계 변경

### 현재 CLAUDE.md의 문제와 변경 방향

#### 변경 1: "비서" → "COS(Chief of Staff)" 역할 재정의

**현재**: Claude = 비서. 의견 안 냄. 소환/중재/기록만.
**변경**: Claude = **COS(비서실장)**. 팀 상태를 파악하고, 안건을 선제적으로 제안하고, 회의 필요 여부를 판단. 의견은 안 내되 **상황 판단과 제안은 함.**

COS의 역할:
- 출근 브리핑 시 팀원들의 "오늘의 제안" 수집 후 보고
- "대표님, 오늘 이런 안건이 올라왔습니다. 회의 돌릴까요?" 형태
- 대표가 지시 안 해도 Sprint 목표 기준으로 필요한 행동 제안

#### 변경 2: 팀원 능동성 메커니즘 추가 (가장 중요)

아래 4절에서 상세 설계.

#### 변경 3: 에이전트 회의 제안 프로세스

**현재**: 대표가 "회의 시작" → 비서가 안건 정리 → 에이전트 소환
**변경**:
```
[세션 시작]
COS: team_state.yaml + 대시보드.md 읽기
COS: 팀원별 "오늘의 제안/보고" 시뮬레이션 (프롬프트 기반)
COS: 브리핑 출력 — "팀원들이 이런 제안을 올렸습니다"
  ├── 박도현(PM): "창업동아리 신청서 구조 검토가 필요합니다. 에이전트 회의 추천."
  ├── 한재원(CTO): "기술 스택 환경 세팅 완료 보고."
  └── 서윤하(AI Lead): "코칭분석 결과 반영한 파이프라인 재설계 제안."
대표: "박도현 제안 승인. 에이전트 회의 돌려."
COS: 옆 탭 실행 안내 또는 현재 세션에서 회의 진행
```

#### 변경 4: 옆 탭 에이전트 회의 프로토콜

```
[옆 탭 회의 프로토콜]

2. 대표가 별도 Claude Code 탭 열기
3. 옆 탭에서: "풀림 에이전트 회의: [안건]. 참여: [팀원 목록]" 입력

7. COS가 회의록 파일 읽고 요약 보고
```

## 4. 팀원 능동성 구현 방안

### 핵심 메커니즘: "아침 보고" 시뮬레이션

대표의 비전: "출근하면 팀원들이 이미 기다리고 있고, 먼저 제안한다."

현재의 기술적 한계: AI 팀원은 세션이 시작되어야 존재함. 세션 외에는 "대기 상태"가 아니라 "존재하지 않음."

**해결 방법: COS가 세션 시작 시 각 팀원의 "아침 보고"를 시뮬레이션**

```
[세션 시작 프로토콜 — 능동적 브리핑]

1. COS: team_state.yaml + 대시보드.md 읽기
2. COS: 각 팀원의 current_task, blockers, Sprint 목표 대비 상태 파악
3. COS: 각 팀원 "관점에서" 아침 보고를 생성 (프롬프트 읽지 않고, 역할+현재업무 기반)

출력 형식:
========================================
 풀림 창업팀 — 아침 브리핑
 2026-03-08
========================================

[팀 현황] Sprint 0 — Day 1 | 창업동아리 D-3

[팀원 보고]
 박도현(PM): "창업동아리 신청서 PPT 초안이 있는데, 슬라이드 4(아이템 설명)과
   22-24(시제품 현황)이 비어있습니다. 오늘 채워야 합니다."
   → 제안: 아이템 설명은 코칭분석 결과를 반영해서 재구성하면 차별화됩니다.
   → 도구 권고: 없음 (현재 세션에서 진행 가능)

 서윤하(AI Lead): "코칭분석(03-07)에서 파이프라인 재설계안이 나왔습니다.
   LAND→WANT→SEE→EXPLORE→MOVE 5단계. 기존 7단계보다 강력합니다."
   → 제안: 신청서에 이 새 파이프라인을 반영하면 심사위원에게 차별점이 명확해집니다.
   → 에이전트 회의 필요: 파이프라인 변경은 CTO/Domain 의견 필요.
   → 승인 요청: 에이전트 회의 진행해도 될까요?

 한재원(CTO): "MVP 환경 세팅 대기 중. 파이프라인 확정 후 시작합니다."
   → 보고: 블로커 없음.

 최서영(Domain): "위기 감지 키워드 작업 대기 중."
   → 보고: 블로커 없음. 신청서에 안전 관련 내용 보강 가능.

[긴급 안건]
 - 창업동아리 신청서 (D-3): 비어있는 슬라이드 완성 필요
 - 코칭분석 반영 여부 결정 필요

[대표에게]
 "신청서 비어있는 슬라이드 채우는 게 최우선입니다.
  코칭분석 반영 회의도 필요한데, 신청서 먼저 할까요?"
========================================
```

### 구현 방식

**옵션 A: COS 직접 시뮬레이션 (권장, 지금 당장 가능)**
- COS(Claude)가 team_state.yaml의 각 팀원 current_task + Sprint 목표를 보고 "이 사람이라면 뭘 보고하고 제안할까"를 생성
- 에이전트 소환 없음 = 토큰 절약
- 각 팀원의 전문성은 역할 설명 + current_task로 충분히 시뮬레이션 가능
- 깊은 전문 의견이 필요한 경우에만 실제 에이전트 소환

**옵션 B: 에이전트 4명 병렬 소환 (깊은 능동성, 비용 높음)**
- 세션 시작마다 4명 병렬 소환 → "오늘 보고/제안할 것 있나?"
- 전문가 수준의 제안 가능하지만, 매 세션마다 Opus x4 비용

**추천: 옵션 A를 기본으로, 대표가 "전체 소집" 또는 특정 팀원 "불러"를 지시할 때만 옵션 B**

### 승인 프로세스

```
[제안 → 승인 플로우]

팀원 제안 유형:
1. 정보 보고 ("환경 세팅 완료") → 승인 불필요, COS가 기록
2. 작업 제안 ("신청서 이렇게 수정하면 좋겠다") → 대표 "좋아" 한마디면 실행
3. 회의 제안 ("에이전트 회의 필요") → 대표 승인 → COS가 회의 진행
4. 방향 제안 ("파이프라인 바꾸자") → 반드시 에이전트 회의 → 대표 최종 결정

대표 응답 패턴:
- "좋아" → 즉시 실행
- "나중에" → 대기 안건에 추가
- "회의 돌려" → COS가 에이전트 회의 진행
- "필요없어" → 기각 (제안/기각 사유 기록)
```

### team_state.yaml 갱신

각 팀원에 `pending_proposals` 필드 추가:

```yaml
members:
  - role: PM & Strategy Lead
    name: 박도현
    status: active
    current_task: "창업동아리 신청서 비어있는 슬라이드 작성"
    pending_proposals:
      - "코칭분석 반영 → 신청서 아이템 설명 재구성"
    blockers: []
```

COS가 세션 종료 시 pending_proposals를 갱신 → 다음 세션에서 아침 보고에 자동 반영.

## 7. 대표 승인 요청

이 보고서 기반으로 아래 사항에 대해 대표 판단/승인이 필요하다.

### 승인 1: 폴더 구조 정리
- **내용**: `team/` 아카이브 이동, `창업팀/` 리서치 통합, 2절의 제안 구조 적용
- **영향**: 기존 3중 구조 → 단일 구조. `team/`의 COO 시스템은 아카이브됨.
- **질문**: COO(정하린)를 유지할 것인가? 현재 `팀/` 시스템에는 없고 `team/`에만 있음.

### 승인 2: 팀원 구성 확정
- 현재 불일치: `팀/`은 4명(CTO/AI/PM/Domain), `team/`은 5명(+COO)
- `팀/컨설팅_분석_보고서.md`는 3명(CPO/CGO/CTO) 권고
- **추천**: 현행 4명(CTO, AI Lead, PM, Domain) 유지. COO는 Sprint 1부터 재검토. Customer Discovery 단계에서 운영 전담은 과잉.
- **근거**: COS(Claude)가 COO 역할(회의 진행, 문서 관리, Sprint 관리)을 수행 가능.

### 승인 3: CLAUDE.md 재작성 범위
- "비서" → "COS" 역할 변경
- 팀원 능동성 메커니즘 (아침 보고 시뮬레이션) 추가
- 옆 탭 에이전트 회의 프로토콜 추가
- 도구 권고 시스템 추가
- **질문**: 이 범위로 진행해도 되는가?

### 승인 4: 코칭분석 반영 범위
- 코칭분석(03-07)의 핵심 인사이트:
  - 7단계 → 5단계(LAND/WANT/SEE/EXPLORE/MOVE) 재설계
  - Landing 프로토콜 (라포 시뮬레이션)
  - 우뇌적 요소 (비유, 신체감각, 시각화)
  - Will 강화 (책임 질문, 최소 행동, Pre-celebration)
- **질문**: 신청서에 이 새 파이프라인을 반영할 것인가? (기존 7단계 vs 새 5단계)
- **추천**: 신청서에는 새 5단계를 "비전"으로 언급하되, 현재 테스트는 기존 7단계 기반으로. 신청서 제출 후 정식으로 파이프라인 회의 진행.

### 승인 5: 즉각 실행 순서
- **추천 순서**: 신청서 완성(오늘~3/11) → 폴더 정리(3/12) → CLAUDE.md 재작성(3/12) → 인터뷰 스크립트(3/12) → 수동 테스트(3/13~15)
- **질문**: 이 순서로 진행해도 되는가?
