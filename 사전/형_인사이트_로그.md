- 하네스 잘 만들면 토큰 소비를 줄이면서 서비스 수준은 유지 가능

**적용 포인트**:
- 풀림 제품 설계 시 하네스 = 토큰 효율 + 일관된 출력 품질 유지 장치
- MRR 목표 설정 시 750만원 → Global 진출 단계적 흐름 참고

**적용 여부**: 사전 반영 완료 (하네스_적합도_이론.md)

## 2025-12-06

**출처**: 카톡 (KERNEL 프롬프트 엔지니어링 프레임워크 공유)

**인사이트**:
- 1,000개 이상 실무 프롬프트 분석 결과 → 성공 패턴 6가지: **KERNEL**
  - K: Knowledge boundary / E: Explicit output / R: Reference style / N: Narrowed scope / E: Explicit constraints / L: Layered structure
- "1 프롬프트 = 1 목표" — 단일 목표 만족도 89%, 다중 목표 41%
- "성공 기준이 명확해야 한다. 내가 검증할 수 없으면 AI도 제대로 못 만든다"

**적용 포인트**:
- 팀원 소환 프롬프트 작성 시 KERNEL 구조 적용
- 풀림 사용자 입력 설계 시 단일 목표 원칙 반영

**적용 여부**: 미적용

## 2026-03-06

**출처**: 카톡 (형 발표 준비 내용 + 철학 논의)

**인사이트**:
- **"직종들의 에고를 하네스로"** — 핵심 명제
  - 디자이너/QA 등 모든 직군이 자기 에고를 최종 프로덕트가 아닌 하네스 구축에 쏟아야 함
  - QA 사례: '내 손을 거쳐야 배포된다'는 에고 → 'QA 자동화 하네스 만들기'로 전환
  - 하네스 본질 = 인간과 LLM의 원활한 상호작용
- 조직: 개인 10x/100x보다 전체 2x 성장이 맞다
- AI 피로감 해결: 익명 보드 기반 'AI 회고' 자리 마련
- **이데아와 온톨로지 (형 원문)**:
  > "온톨로지는 플라톤이 말하는 그림자와 같다. 발산하여 온톨로지를 재정의할 때야 진정한 이데아로 향하는 것. AI를 이용한 unknown unknowns 해결: 보상 없이 에이전트 시뮬레이션을 여러 번 돌리면 gut driven method가 구축되고 unknown unknowns가 나온다."
- 상규: "생산성도 기존 온톨로지니까" — 생산성의 정의 자체가 바뀔 수 있음

**적용 포인트**:
- 풀림 팀원 모두: 에고를 제품이 아닌 하네스(AI 파이프라인 구축)에 두도록 방향 설정
- 에이전트 반복 시뮬레이션 = unknown unknowns 발굴 수단으로 활용

**적용 여부**: 미적용

**인사이트 (삶/태도)**:
- "오만해지는 자리는 백해무익. 항상 결핍을 느끼는 자리로 가라"
- 비전 있는 친구는 같이 고민 / 멈춰있는 친구 모임은 20살 얘기만 → 관계 필터링 자연스럽게 됨

- 기술을 깊이 파면 결국 철학으로 간다

**적용 포인트**:

- 비트겐슈타인 논고 독서 후 AI 설계 철학에 반영 검토

## 2026-03-16

**출처**: 형 블로그 — "Ouroboros 시리즈 02 — 구조" (같이 읽기 세션)

**오늘 물어본 것들**:
- AC(Acceptance Criteria)가 뭔지 → 완료 기준 목록. 서브에이전트 아님
- 오케스트레이션 → 여러 세션 조율해서 결과 모아주는 것
- Dependency graph → 선후 관계 그래프 ("이게 끝나야 저게 시작")
- Event 수집 → 완료 신호 (AC 끝나면 "나 끝났어" 신호 보냄)
- 블로킹 vs 비동기+폴링 → 배달 문 앞 대기 vs 딴 거 하다가 10분마다 확인
- Hook이 뭔지 → 특정 시점에 자동 실행되는 코드 (LLM이 무시 불가)
- fork, 바이트 스트림 → OS 프로세스 복제/통신 방식
- **미해결**: 비동기 폴링에서 메인 세션이 그동안 실제로 뭘 할 수 있는지 → 형에게 물어볼 것

**인사이트**:
- **작은 깨달음**: MCP는 양방향이다. 원래 LLM→도구 방향이었는데, 도구→LLM도 된다. Codex 같은 다른 런타임에서도 작동.
- **큰 깨달음**: Ouroboros 구조가 OS 프로세스 모델과 동일. 스케줄러, 프로세스, 메시지 패싱이 그대로 있음. 새로운 것을 만든 게 아니라 검증된 패턴의 재발견.
- → "기존 도구/개념을 쓰는 프레임을 깨면 혁신이 가능하다"는 인사이트
- → 철학이 AI 설계로 이어지는 패턴 (OS 설계 원리 → LLM 오케스트레이션)
- **글에 대한 의견**: 인사이트 자체는 매우 좋음. 다만 같은 설명이 3번 반복되어 후반부 디테일(비동기 폴링 등)을 챙기려는 동기가 줄어듦. 인사이트 위주로 압축했으면 더 임팩트 있었을 것.

**적용 포인트**:
- 도구 설계 시 "이 도구가 LLM을 쓸 수도 있다"는 역방향 발상 적용 가능
- 새 시스템 설계 전 기존 CS 패턴(OS, DB, 네트워크)과 비교해볼 것

**적용 여부**: 미적용
