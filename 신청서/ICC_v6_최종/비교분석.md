## 심사위원 공통 지적 (3개 버전 모두)

1. **유료 전환율 20% 근거 없음** - SaaS 평균 2~5%의 4~10배. 출처 필요
2. **TAM 정의 오류** - 경쟁사 매출 합산 ≠ TAM. "확인 매출 합산 기준"으로 표기
3. **1인 체제 지속 가능성** - 코드 유지보수, 번아웃, 장애 대응
4. **12개 경쟁사 비교표 미첨부** - 주장만 있고 근거 없음
5. **BEP 13명에 인건비 미포함** - 서버 비용만의 BEP

## 각 버전 강점/약점

### v6-A (스토리텔링) - 추천
강점: AI 확률 최저, 개인 경험이 진정성 생성, "나도 그랬다"가 심사위원 공감 유도, 리스크 자발적 인정
약점: 데이터가 서술에 묻힘, 수치를 빠르게 훑기 어려움

### v6-B (데이터 중심)
강점: Unit Economics 최상세, 기업인 점수 최고(78), 수치 기반 설득
약점: AI 확률 82%(최악), 개인성 부재, "누가 써도 될 것 같은 글"

### v6-C (문제-해결)
강점: 구조 직관적, 교수 점수 최고(72), 읽기 쉬움
약점: "문제-해결" 구조 자체가 AI에서 가장 흔한 패턴, AI 확률 72%

## 추천

추천 버전: **v6-A (스토리텔링형)**

이유:
1. AI 확률이 가장 낮다 (심사위원이 "AI가 써준 것 같다"고 느낄 위험 최소)
2. ICC 심사의 핵심 질문 "이 사람이 왜 이걸 하는가"에 가장 강하게 답한다
3. "비전공자가 직접 만들어서 배포했다"가 자연스럽게 녹아 있다
4. v6-B의 BEP 계산 공식을 최종본에 이미 반영하여 데이터 약점 보완

## 발표 준비 포인트 (심사위원 공통 질문)

1. "유료 전환율 20% 근거?" → 세계관 몰입 + 만원 이하 심리가격이 높은 전환율의 근거. 보수적 5%로도 BEP 충분
2. "BEP에 인건비 없는데?" → 예비창업 단계, 자체 자금 3천만 원으로 생활비 충당. 서비스 유지비만으로 BEP 산출
3. "AI가 코드 짜줬으면 유지보수는?" → Claude Code 활용하면 디버깅도 같은 방식. ICC 멘토링으로 기술 자문 가능
4. "12개 비교표?" → 발표 때 슬라이드 또는 보조자료로 첨부
