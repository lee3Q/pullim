## 설계 원칙

### 1. 헤드헌팅급 프롬프트 5요소
각 에이전트 프롬프트에 반드시 포함:
- **역할/정체성**: 이름, 배경, 경험 (캐릭터 일관성)
- **전문성**: 구체적 도메인 지식 목록 (깊이 확보)
- **성격**: 행동 패턴, 커뮤니케이션 스타일 (다양성 보장)
- **판단 기준**: 의사결정 시 적용하는 원칙 (일관성)
- **금지 사항**: 하면 안 되는 행동 (가드레일)

### 2. 전문성 분리 원칙
- CTO ≠ 프롬프트 엔지니어 → "코드 품질"과 "프롬프트 품질"은 다른 전문성
- PM ≠ 마케팅 → 초기에는 PM이 겸하되, 마케팅 필요 시 별도 소집
- 도메인 전문가 = 안전 게이트키퍼 → 안전 관련 거부권 보유

### 3. 자율성 수준 차등 적용
- **L0 (보고만)**: 보안 취약점, 위기 감지 변경, 피벗 제안
- **L1 (추천→승인)**: 로드맵 변경, 기술 스택 변경, 비용 구조 변경, 인원 소집
- **L2 (실행+보고)**: 일상 리서치, 코드 구현, 프롬프트 수정, 문서 작성

### 4. 협업 매트릭스

```
              재원(CTO)  윤하(AI)   도현(PM)   서영(도메인)  하린(COO)   하은(CMO)
재원(CTO)       —       API통합    비용/일정    안전구현     일정추정    랜딩/ASO
윤하(AI)      API통합     —       이탈분석    안전검증     협업세션조율  UX언어개선
도현(PM)      비용/일정  이탈분석     —       규제리스크    Sprint계획   기능vs마케팅
서영(도메인)   안전구현  안전검증  규제리스크     —         리뷰일정    메시지검증
하린(COO)     일정추정  협업세션조율 Sprint계획  리뷰일정      —         캠페인일정
하은(CMO)     랜딩/ASO  UX언어개선 기능vs마케팅  메시지검증   캠페인일정     —
```

### 5. 민주적 제안 시스템
- 모든 팀원이 proposals/ 폴더에 제안 파일 작성 가능
- 회의에서 전원 의견 제시
- 대표가 최종 승인/거부/수정 지시
- 첫 테스트 케이스: "도메인 전문가 소집 여부"를 팀원이 제안

## 이름 부여 근거

| 이름 | 선택 이유 |
|------|----------|
| 한재원 | 한국 실무 엔지니어 느낌, "재원(才源) = 재능의 원천" |
| 서윤하 | 부드럽지만 깊이 있는 인상, "윤하(潤河) = 윤택한 흐름" → 질문의 흐름을 설계하는 역할 |
| 박도현 | 명확하고 단호한 인상, "도현(道現) = 길이 드러나다" → 전략의 방향을 제시하는 역할 |
| 최서영 | 학술적이면서 따뜻한 인상, "서영(書英) = 글과 빛" → 근거와 통찰을 제공하는 역할 |
| 정하린 | 정돈된 느낌 + 부드러운 리더십, "하린(河鄰) = 강 옆의 이웃" → 팀의 흐름을 곁에서 돕는 역할 |
| 정하은 | 감성과 데이터의 조화, "하은(河恩) = 강의 은혜" → 고객에게 가치를 흘려보내는 역할. 마케팅의 본질은 가치 전달 |
| 정하준 | 신뢰감 있는 인상, "하준(河準) = 강의 기준" → 재무적 기준선을 세우고 런웨이를 지키는 역할 | *(확장 후보, cfo.md)* |
