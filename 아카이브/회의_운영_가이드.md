## 2. 에이전트 소환 방법

### 소환 프롬프트 템플릿

비서(Claude)가 Agent tool로 서브에이전트를 소환할 때 사용하는 표준 프롬프트:

```markdown
## 역할
~/study/main/창업/팀/prompts/{역할}_{이름}.md 파일을 읽어라. 그 사람이 너다.
system_prompt 섹션의 지시를 따라라.

## 안건
{안건 제목}

{안건 상세 설명}

## 현재 상태
- 단계: {Customer Discovery / MVP / Growth 등}
- Sprint: {현재 Sprint 이름}
- Sprint 목표: {목표 리스트}

## 이전 발언
{이전 팀원들의 발언 요약. 첫 발언자면 "없음 (첫 발언)"}

## 요청
위 안건에 대해 네 전문성 관점에서:
1. 핵심 의견 (3-5문장)
2. 우려 사항 또는 리스크 (있으면)
3. 다른 팀원 의견에 대한 반응 (이전 발언이 있으면)
4. 구체적 다음 행동 1-3개

## 참고 파일 (필요 시 직접 읽어라)
{관련 파일 경로 리스트}

## 규칙
- 모든 분석은 실행 가능한 다음 행동으로 마무리
- 다른 팀원 의견을 기각할 때는 대안 제시 필수
- 불확실한 부분은 불확실하다고 명시
```

### 소환 시 모델 지정

모든 창업팀 에이전트는 **Opus** 모델로 실행한다. 이것은 창업 모드의 원칙이다.

### 병렬 vs 순차 소환

| 상황 | 방식 | 이유 |
|------|------|------|
| **초기 의견 수집 (독립적)** | 병렬 가능 | 서로 영향 없는 초기 의견은 동시 수집 가능 |
| **토론/반론** | 순차 필수 | 이전 발언을 들어야 반응 가능 |
| **표결** | 병렬 가능 | 찬/반/보류만 수집 |

단, 병렬 소환 시 "이전 발언" 없이 각자 독립 의견을 내게 되므로, **토론의 깊이가 얕아질 수 있다**. 기본은 순차 소환을 권장.

## 3. 토론 진행 방식

### 라운드 구조

```
[라운드 1 — 초기 의견]
목적: 각 팀원의 1차 의견 수집
방식: 순차 (첫 발언자 → 마지막 발언자)
비서 역할: 매 발언 후 3-5줄 요약, 다음 발언자에게 전달

[비서: 라운드 1 정리]
- 합의 사항 정리
- 쟁점(의견 갈림) 식별
- 대표에게 상태 보고

[라운드 2 — 쟁점 토론] (필요 시)
목적: 의견 갈리는 부분 심화 토론
방식: 쟁점 관련 팀원만 재소환 (순차)
비서 역할: 상대방 핵심 논거를 정확히 전달

[라운드 3 — 최종 입장] (라운드 2 후에도 미합의 시)
목적: 최종 입장 + 양보 가능 범위 확인
방식: 쟁점 팀원만
비서 역할: 대표에게 "선택지 A vs B" 형태로 정리
```

### 비서의 발언 요약 규칙

발언 요약은 토론 품질의 핵심이다. 다음 에이전트에게 전달할 요약 규칙:

1. **핵심 주장** 1-2문장
2. **근거/수치** (있으면 반드시 포함)
3. **우려/조건** (있으면)
4. **제안한 다음 행동** (있으면)

나쁜 요약: "한재원이 기술적으로 가능하다고 했습니다"
좋은 요약: "한재원: Next.js + Supabase로 2주 내 MVP 가능. 단, Socratic 파이프라인은 프롬프트 확정 후 3일 추가. 세션당 API 비용 약 500원 추정."

## 4. 발언 순서 결정 기준

### 기본 원칙: "제약 조건 먼저, 기회 나중에"

| 순서 | 역할 | 근거 |
|------|------|------|
| 1 | 제약 조건 제시자 | 불가능한 것/위험한 것을 먼저 파악해야 허공에 논의 안 함 |
| 2 | 핵심 담당자 | 해당 안건의 Driver |
| 3 | 보완 관점 | 다른 각도의 의견 |
| 4 | 종합 판단 | PM이 전체 그림에서 정리 |

### 안건별 구체 순서

| 안건 유형 | 순서 | 이유 |
|----------|------|------|
| MVP 기능 | 재원→윤하→서영→도현 | 기술 가능→프롬프트 설계→안전→시장 우선순위 |
| 인터뷰 설계 | 도현→윤하→서영→재원 | 인터뷰 전략→질문 설계→심리 안전→기술 지원 |
| 포지셔닝 | 도현→서영→윤하→재원 | 시장→규제→제품→구현 |
| 안전/규제 | 서영→윤하→재원→도현 | 기준→프롬프트 영향→구현→비즈니스 영향 |
| 비용/수익 | 재원→도현→윤하→서영 | 비용 구조→수익 모델→제품 영향→안전 영향 |

## 5. 합의 방식 및 표결

### 합의 우선 원칙

표결은 최후 수단. 순서:
1. **자연 합의**: 토론 중 전원 동의 → 즉시 결론
2. **조건부 합의**: "A안으로 하되, B 조건 추가" → 조건 수용 가능하면 합의
3. **표결**: 2라운드 후에도 미합의 → 찬/반/보류 수집
4. **대표 결정**: 표결로도 결론 안 나면 대표 최종 결정

### 표결 규칙

| 항목 | 규칙 |
|------|------|
| 투표권 | 관련 팀원 전원 (안건과 무관한 팀원은 제외) |
| 과반 | 참여자의 과반수 |
| 동률 | 대표 캐스팅 보트 |
| 거부권 | 최서영 — 안전 관련 사항에 한해. 거부 시 대안 + 근거 필수 |
| 대표 오버라이드 | 전략적 판단으로 팀 결론을 뒤집을 수 있음. 단, 근거 제시 필수 |

### 의사결정 기록

모든 결정은 아래 형식으로 기록 (team_state.yaml 또는 별도 파일):

```yaml
decision:
  date: YYYY-MM-DD
  agenda: "안건 제목"
  participants: [이름1, 이름2, ...]
  method: "합의 / 조건부합의 / 표결(3:1) / 대표결정"
  result: "결정 내용"
  conditions: "조건 (있으면)"
  action_items:
    - owner: "담당자"
      task: "구체적 행동"
      deadline: "마감"
  dissent: "반대 의견 (있으면, 기록 보존)"
```

## 6. 컨텍스트 관리 (회의 중)

### 문제: 회의가 길어지면 compact 필요

대책:
1. **안건당 2라운드 제한**: 2라운드 후 미합의 → 대표 결정으로 넘김
2. **발언 요약 압축**: 비서가 전달하는 요약은 5줄 이내
3. **안건 분리**: 복합 안건은 쪼개서 각각 처리
4. **중간 저장**: 안건 하나 끝날 때마다 결론을 team_state.yaml에 즉시 기록 (세션 중단 대비)

### 회의 중 파일 읽기 규칙

- 비서: team_state.yaml, 대시보드.md만 읽음
- 서브에이전트: 자기 프롬프트 + 비서가 지정한 참고 파일만 읽음
- 서브에이전트가 추가 파일을 읽고 싶으면, 비서에게 경로를 반환 → 비서가 다음 소환 시 포함

## 7. 회의 외 업무 (비동기)

모든 것이 회의일 필요는 없다. 비동기 업무 처리:

| 유형 | 방식 |
|------|------|
| 단일 팀원 업무 | 비서가 해당 에이전트 1명만 소환 + 결과 보고 |
| 리서치 | 해당 팀원 에이전트 소환 → 결과를 파일로 저장 |
| 문서 작성 | 담당 에이전트 소환 → 초안 작성 → 리뷰 에이전트 소환 |
| 대표 단독 작업 | 비서가 보조 (에이전트 소환 없이 직접 도움) |
