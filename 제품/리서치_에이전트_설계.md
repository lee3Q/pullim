# 리서치 에이전트 설계

> 날짜: 2026-03-20
> 기반: 끝판왕_파이프라인_설계 (1단계 리서치 + 2단계 검증)
> 관련 코드: pullim/src/lib/llm/agent-prompts.ts (V2 — 리서치 없음, 신규)

---

## 역할

파이프라인 1~2단계를 담당. 사용자의 고민에 대해 **실제 데이터**를 수집하고, 팩트체크 후 구슬 분석에 넘긴다. V2에는 없던 완전 신규 모듈.

세계관에서: "현자가 두루마리를 펼치는" 단계.

---

## 아키텍처

```
[사용자 고민 + concern_type]
         │
         ▼
  ┌─────────────┐
  │ 쿼리 생성기  │ ← Sonnet
  │ (3개 쿼리)   │
  └──────┬──────┘
         │
    ┌────┼────┐
    ▼    ▼    ▼
  [Tavily] [Tavily] [Tavily]  ← 병렬 검색
    │    │    │
    └────┼────┘
         ▼
  ┌─────────────┐
  │  결과 구조화  │ ← Sonnet
  │ + 출처 보존   │
  └──────┬──────┘
         │
         ▼
  ┌─────────────┐
  │  팩트체크    │ ← Gemini Pro (Judge)
  │  (비노출)    │
  └──────┬──────┘
         │
         ▼
  [검증된 리서치 데이터] → 3단계(논의 1)로 전달
```

## 1단계: 쿼리 생성

### 프롬프트

```
사용자 고민: {concern}
고민 유형: {concern_type}
선택된 구슬: {selected_crystals} (있으면)

이 고민에 대해 데이터 기반 분석을 위한 검색 쿼리 3개를 생성해라.

쿼리 설계 원칙:
1. 통계/수치 쿼리 — 관련 통계, 확률, 비용, 비율 (예: "한국 1인 창업 3년 생존율 2025")
2. 사례/경험 쿼리 — 유사 상황의 실제 사례, 후기, 경험담 (예: "AI SaaS 1인 창업 후기 reddit")
3. 전문가/학술 쿼리 — 해당 분야 전문가 견해, 연구 결과 (예: "decision fatigue cognitive psychology meta-analysis")

규칙:
- 한국어 + 영어 쿼리를 섞어라 (한국 맥락 + 글로벌 데이터)
- 너무 넓은 쿼리 금지 ("창업" ❌ → "한국 AI SaaS 1인 창업 생존율 2025" ✅)
- 고민 유형에 따라 쿼리 방향 조정

JSON으로만 출력:
{
  "queries": [
    { "type": "statistics", "query": "...", "language": "ko" },
    { "type": "cases", "query": "...", "language": "en" },
    { "type": "expert", "query": "...", "language": "ko" }
  ]
}
```

### concern_type별 쿼리 힌트

| concern_type | 통계 방향 | 사례 방향 | 전문가 방향 |
|-------------|----------|----------|------------|
| career | 직군 전환율, 연봉 분포 | 이직 성공/실패 후기 | 커리어 코칭 연구 |
| relationship | 갈등 해결 통계 | 유사 관계 패턴 사례 | 관계 심리학 연구 |
| finance | 투자 수익률, 비용 구조 | 유사 재무 결정 사례 | 행동경제학 연구 |
| burnout | 번아웃 통계, 회복 기간 | 번아웃 회복 사례 | 산업심리학 연구 |
| legal | 판례, 법조문, 승소율 | 유사 분쟁 해결 사례 | 법률 해석 |
| general | 의사결정 관련 통계 | 유사 고민 해결 사례 | 의사결정 과학 |

## 2단계: 웹 검색 (Tavily API)

### API 선택 근거

| API | 무료 한도 | 품질 | 선택 |
|-----|----------|------|------|
| Tavily | 1,000회/월 | 높음 (LLM 최적화) | **1순위** |
| Perplexity API | 유료 only | 높음 | 2순위 (Tavily 소진 시) |
| Google Custom Search | 100회/일 | 중간 | 3순위 (폴백) |

### 호출 명세

```typescript
interface TavilySearchParams {
  query: string;
  search_depth: "basic" | "advanced";  // basic: 빠름, advanced: 깊음
  max_results: 5;
  include_answer: true;   // Tavily가 자체 요약 제공
  include_raw_content: false;  // 원문 불필요 (토큰 절약)
}

interface TavilyResult {
  answer: string;          // Tavily 자체 요약
  results: {
    title: string;
    url: string;
    content: string;       // snippet
    score: number;         // 관련성 점수
    published_date?: string;
  }[];
}
```

### 검색 전략

```
쿼리 3개 → Tavily 병렬 호출 (Promise.allSettled)
→ 각각 max 5결과 = 최대 15개 소스
→ score 0.7 이상만 필터
→ 중복 URL 제거
→ 최종 ~8-10개 소스
```

### 할당량 관리

```typescript
// 월 1,000회 Tavily 무료
// 세션당 3회 = ~333세션/월 (충분)
// 초과 시: search_depth를 basic으로 변경 (빠르지만 얕음)
// 그래도 초과: 검색 스킵 → "현자의 기억"만으로 진행 (리서치 없는 모드)

const MONTHLY_LIMIT = 1000;
const QUERIES_PER_SESSION = 3;

async function checkQuota(): Promise<"full" | "basic" | "skip"> {
  const used = await getMonthlyUsage();
  if (used < MONTHLY_LIMIT * 0.8) return "full";      // advanced
  if (used < MONTHLY_LIMIT) return "basic";             // basic
  return "skip";                                         // 검색 스킵
}
```

## 3단계: 결과 구조화

### 프롬프트

```
[검색 결과]
{raw_tavily_results}

[구조화 규칙]
아래 형식으로 정리해라:

1. 데이터 카드 (3~5개)
   - 각 카드: 제목 + 핵심 수치/사실 1개 + 출처 URL
   - "~에 따르면" 형식으로 출처 명시
   - 수치가 없으면 만들지 마라

2. 상충 데이터
   - 소스 간 서로 다른 주장이 있으면 명시
   - "A는 ~라고 하는데, B는 ~라고 한다"

3. 데이터 부족 영역
   - 검색해도 안 나온 것 (구슬 분석에서 "데이터 없음" 명시용)

JSON 출력:
{
  "cards": [
    {
      "title": "카드 제목",
      "fact": "핵심 수치/사실",
      "source": { "name": "출처명", "url": "URL" },
      "confidence": "high" | "medium" | "low"
    }
  ],
  "conflicts": [
    { "topic": "주제", "source_a": "주장A", "source_b": "주장B" }
  ],
  "gaps": ["데이터 없는 영역"]
}
```

## 4단계: 팩트체크 (Judge)

### 역할

Gemini Pro가 독립적으로 리서치 결과를 검증한다. 사용자에게는 비노출.

### 프롬프트

```
[리서치 요약]
{structured_research}

[팩트체크 지시]
1. 각 데이터 카드의 수치/주장이 출처와 일치하는지 확인
2. 오래된 데이터(2년 이상)에 플래그
3. 샘플 크기가 작거나 신뢰도 낮은 출처에 플래그
4. 인과관계를 상관관계로 잘못 해석한 경우 플래그

JSON 출력:
{
  "verified": [
    { "card_index": 0, "status": "pass", "note": "" }
  ],
  "flagged": [
    { "card_index": 2, "reason": "2019년 데이터, 최신 아님", "action": "caveat" }
  ],
  "overall_confidence": "high" | "medium" | "low"
}

action 옵션:
- "pass": 사용 OK
- "caveat": 사용하되 주의 문구 추가 ("~년 기준")
- "remove": 신뢰 불가, 제거
```

### 팩트체크 후 처리

```
flagged + action="caveat" → 카드에 주의 문구 삽입
flagged + action="remove" → 카드 제거
overall_confidence="low" → 캐릭터가 "기록이 흐릿하군..." 톤으로 전달
```

## 폴백 시나리오

### Tavily 실패

```
Tavily 실패 → Google Custom Search 시도
Google도 실패 → 리서치 스킵
→ 캐릭터: "두루마리가 낡아 글씨를 읽기 어렵군. 자네의 이야기만으로 들여다보겠네."
→ 4단계(구슬 분석)에서 리서치 데이터 없이 진행 (분석 프롬프트에서 research_summary="리서치 데이터 없음")
```

### 팩트체크 실패 (Judge 모델 에러)

```
Judge 실패 → 팩트체크 스킵
→ 리서치 결과를 unverified로 마킹
→ 구슬 분석 프롬프트에 "이 데이터는 미검증" 명시
→ 사용자에게는 드러나지 않음
```

### 검색 결과 0건

```
3개 쿼리 모두 결과 없음 → 극히 드문 케이스
→ Sonnet이 쿼리를 더 넓게 재생성 (1회 재시도)
→ 여전히 없으면 리서치 스킵 모드
```

## 세션 데이터 흐름

```typescript
// research.ts가 반환하는 최종 결과
interface ResearchOutput {
  // 원본
  queries: SearchQuery[];
  raw_results: TavilyResult[];

  // 구조화
  cards: DataCard[];
  conflicts: DataConflict[];
  gaps: string[];

  // 팩트체크
  verification: {
    overall_confidence: "high" | "medium" | "low";
    flagged_indices: number[];
  };

  // 메타
  search_mode: "full" | "basic" | "skip";
  total_sources: number;
  tavily_calls_used: number;
}
```

이 ResearchOutput이 세션 객체에 저장되고, 이후 단계에서 참조:
- 3단계(논의 1): cards → UI 데이터 카드
- 4단계(구슬 분석): summary → 분석 프롬프트 입력
- 9단계(결론): sources → 결론 문서에 출처 첨부
